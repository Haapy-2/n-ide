- 점검 뒤 perf.sh 두 번(2026-11-17, 부하 평균 5 안팎): 앱 실행 530.5ms·549.6ms **미달**, 대기 메모리 74·76MB, 나머지 통과. 표의 앱 실행 줄은 11b 뒤(부하 2.6) 값이다.
- 실시간 키 입력 줄은 메인 스레드 몫(입력·본문 복사·세기 작업 시작·그리기)만 잰다. 10만 자 세기(9.5ms)는 밖에서 돈다.
- 앱 실행은 경계값이라 기기 상태에 따라 미달로 바뀔 수 있다(17단계).
- **대기 메모리 측정 실패(알려진 문제)**: perf.sh의 메모리 단계에서 앱이 30초 안에 꺼져 있었다(이번 포함 두 번). 같은 빌드를 손으로 띄우면 35초 넘게 살아 있고 88MB. 크래시 기록 없음. 실행 측정 직후 바로 띄우는 순서 탓으로 보이나 원인 미확인 → 17단계 측정 정비 때 본다.
- 설정 바꾸기는 SPEC에 목표가 없어 슬라이더를 끄는 동안 한 프레임(16ms)을 기준으로 뒀다.
- perf.sh는 같은 앱(같은 번들 ID)이 떠 있거나 기기가 바쁠 때 실행 측정이 흔들린다: 손 확인용 앱을 켜 둔 채 잰 1회차는 실행 6번 모두 10초 초과·메모리 14MB, 앱을 끈 직후(부하 평균 8.5) 2회차는 중앙값 1,771ms·2번 초과·메모리 측정 실패, 3회차(부하 3.3)는 위 표. 손으로 한 번 띄우면 정상(75MB). 잴 때는 다른 앱 실행을 끈다.
- 글자 수 계산은 SPEC에 목표가 없어 "입력 멈춤 뒤 한 프레임(16ms)"을 기준으로 뒀다. 메인 스레드 밖에서 돈다.
- 작품 열기 0.7→1.3ms: project.json에 회차별 글자 수가 들어가 커졌다.
- 9단계 때 대기 메모리 86MB는 흔들림: 이전 커밋과 번갈아 3번씩 재면 이전 70·74·76MB, 이번 84·75·75MB.
- 메모리 측정 방법이 바뀌었다: 전에는 macOS가 기억한 창 크기(이번 기기 1367×994)로 쟀고 90~112MB로 흔들렸다. 이제 창을 1100×760으로 고정한다. 그래픽 버퍼(IOSurface)가 33MB → 19MB. 앱 코드가 줄어든 것은 아니다.
- 앱 실행: 수정 전후 같은 때 15번씩 두 번 비교해 중앙값 577·539ms(이전) 대 569·546ms(수정) → 속도 차이 없음. 같은 날 오전에는 이전 코드가 483~499ms였다. 기기 상태에 따라 500ms 위아래를 오간다. 17단계에서 구간별로 재고 줄인다(`docs/PERFORMANCE.md` 6장).
- perf.sh 실행 측정에 10초 제한이 생겨 멈춰도 끝까지 돈다. 이번에는 멈춘 실행 없음.

## 미달 원인 조사 (2026-11-10)

- 대기 메모리는 **본문과 거의 무관**하다. 같은 조건에서 500회차 작품 139MB, 1회차 300자 작품 139MB, `backgroundExtensionEffect`를 꺼도 138MB, 작품 선택 창만 띄워도 168MB.
- 큰 덩어리: IOSurface 56~75MB(창·레이어 그래픽 버퍼, 리퀴드 글래스 합성 포함으로 추정), Malloc Small 약 50MB(출처 미확인). 나머지는 합쳐 20MB 남짓.
- 즉 SwiftUI 창 + 리퀴드 글래스의 바탕 비용으로 보이며, 앱 코드가 본문을 쌓아 두는 문제는 아니다. 정확한 출처는 Instruments로 봐야 한다.
- 앱 실행 718ms에는 작품 선택 창을 만든 뒤 작업 공간 창으로 바꾸고 본문을 읽는 과정이 다 들어 있다. 구간별 내역은 아직 안 쟀다.
