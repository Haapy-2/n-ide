요구사항 원문은 [SPEC.md](SPEC.md), 디자인 값은 [DESIGN.md](DESIGN.md).

## 3. 순서 조정 제안 (SPEC 10장 권장 순서와 다른 점)

1. **작품 열기와 사이드바 목록을 편집기보다 먼저** 만든다. 편집할 회차를 고르는 화면이 있어야 편집기를 실제 상황에서 확인할 수 있다.
2. **성능 측정 도구를 3단계에 일찍** 만든다. 그래야 이후 모든 단계 보고에 측정 표를 붙일 수 있다.
3. **"회차 관리와 자동 저장"을 둘로 나누고 자동 저장을 먼저** 한다. 저장을 편집기 바로 다음에 검증하라는 SPEC 취지를 따른 것이다.
4. **스냅샷을 검색·바꾸기보다 먼저** 만든다. 전체 바꾸기가 실행 직전에 스냅샷을 찍어야 하기 때문이다.
5. **설정 창을 따로 한 단계**로 둔다. 편집기 단계를 작게 유지하려는 것이다. 그 전까지는 DESIGN.md 기본값으로 고정된다.

### 단계별 내용

**1. 앱 뼈대** — `NovelEditor.xcodeproj`(앱 타깃, 앱 테스트 타깃), NovelCore 빈 패키지 연결, `Scripts/build.sh`·`run.sh`·`test.sh`(로그는 `build/logs/`), 앱 이름 한곳 관리, 색 토큰 파일, Pretendard 번들(공식 저장소에서 받아 `App/Resources/Fonts/`에 라이선스와 함께), 창 구조(사이드바 + 편집 영역 자리) 와 빈 화면 안내, `docs/PROGRESS.md` 생성, 디자인 스냅샷 생성 방식 확정.

**2. NovelCore 저장 기본** — 모델(작품, 회차, 노트), `project.json` 읽기/쓰기와 `schemaVersion`, 원자적 쓰기, 회차 본문 읽기/쓰기(UTF-8), 고유 ID 파일 이름, 모르는 상위 버전 열기 거부. 단위 테스트.

**3. 저장 순서와 복구** — 회차별 저장 줄(한 번에 하나씩)과 변경 번호, 늦게 끝난 옛 저장이 최신을 덮지 못하는 것을 재현하는 테스트, `project.json.bak` 유지, 깨진 `project.json` → 백업 → `episodes/`로 목록 재구성, 저장 실패 재시도. 단위 테스트.

**4. 작품 선택 창과 사이드바, 성능 도구** — 실행하면 뜨는 작품 선택 창(최근 작품 목록, 새 작품, 다른 위치에서 열기), 작품을 고르면 작업 공간 창으로 이동, "작품 전환…" 메뉴, 사이드바 회차 목록(번호, 제목, 글자 수 자리), `project.json`만 읽고 본문은 읽지 않기. `make-dummy-novel`(500회차 × 5,000자, `build/perf/` 아래 생성), `Scripts/perf.sh`, "500회차 열기" 측정.

**5. 편집기와 한글 입력** — `NSTextView`(TextKit 1 명시) 래퍼, 편집 영역 기본값(본문 폭 고정, 줄·문단 간격, 위아래 여백, 마지막 줄을 가운데까지 올리는 아래 여백), 선택 회차만 읽어 표시, 회차 전환 시 실행 취소 기록 비우기. `docs/checklist-hangul.md` 작성. "키 입력", "회차 전환", "앱 실행", "대기 메모리" 측정 추가.

**6. 자동 저장** — 입력이 멈추면 저장, 회차 전환·창 비활성화·앱 종료 때 저장, 종료 시 진행 중 저장 완료 대기, 실패 시 재시도 후 눈에 띄는 표시, 실패 상태로 닫으면 경고. 조합 중 저장이 조합을 끊지 않는지 확인.

**7. 회차 관리** — 추가, 이름 변경, 삭제(확인 → 휴지통, 휴지통 이동 실패 시 중단), 드래그 순서 변경. 각 동작의 메뉴와 단축키.

**8. 외부 변경 처리** — 창 활성화 때와 저장 직전에 파일 변경 확인, 앱 쪽 변경이 없으면 조용히 다시 읽기, 양쪽 다 바뀌었으면 앱 쪽을 스냅샷으로 남기고 선택 묻기.

**9. 글자 수와 상태 표시줄** — 공백 포함/제외, 표시 방식(포함/제외/둘 다)과 목표 기준(포함/제외) 선택 설정(백그라운드 계산, 먼저 전체 계산 속도를 재고 느리면 증분 계산), 회차별 목표와 진행률, 사이드바 글자 수, 상태 줄 흐려짐/다시 나타남, 저장 중·실패 표시.

**10. 설정 창** — 본문 글꼴 3종, 글자 크기, 줄 간격, 문단 간격, 본문 폭, 글자 수 표시 방식·목표 기준(결정 사항 3), **사이드바 뒤로 창(다른 앱·바탕화면) 비치기 켜기/끄기**(기본 켬, 2026-11-10 사용자 요청. 효과는 6단계 후속 수정에서 이미 들어갔고 키는 `AppSettingKey.sidebarSeesThroughWindow`). 설정 저장 위치는 결정 사항 6 참고.

**11. 버전 스냅샷과 비교** — 수동 찍기(메모), 자동 찍기(기본 30분)와 회차를 떠날 때 찍기, 보관 개수 설정(10~100, 기본 50, 자동·떠날 때만, 오래된 것부터 바로 삭제), 과거↔현재 비교(GitHub 모양, 떠 있는 판), 복원과 복원 취소, 편집기 줄 번호 설정. 2026-11-12 사용자와 정함, 10장.

**12. 작품 전체 검색** — 백그라운드에서 모든 회차 검색(줄 단위, 대소문자 옵션), 결과 목록, 클릭하면 해당 회차의 위치로 이동. 첫 검색/두 번째 검색 측정.

**13. 전체 바꾸기** — 대상 개수 표시와 확인, 실행 직전 해당 회차 전부 스냅샷, 한 번의 실행 취소로 전부 되돌리기(어려우면 스냅샷 복원 안내). 자세한 계획은 14장(9장 4번보다 앞선다).

**14. 집중 모드와 타자기 스크롤** — 사이드바·상태 줄 숨김, 입력 줄을 세로 가운데 근처로 유지(조합을 끊지 않는지 확인).

**15. 설정 노트 분할 화면** — 노트 목록, 노트 추가/이름 변경/삭제, 본문 옆 분할 표시, 노트 자동 저장.

**16. 내보내기** — 선택 회차 또는 전체, txt/md, 한 파일로 합치기("N화 제목" + 빈 줄) 또는 회차별 파일.

**17. 마무리 최적화** — 성능 목표 전체 측정과 미달 항목 보고, 메뉴·단축키 전체 점검, 앱 아이콘, 문서 정리.

## 5. 세부 기준 (SPEC 7장 제안값, 확인 필요)

SPEC에 있던 값:

- **글자 수**: `String.count`(보이는 글자 단위). "공백 포함"은 줄바꿈만 빼고 모두, "공백 제외"는 공백·탭·줄바꿈을 뺀다. 조합 중인 글자도 한 글자.
- **자동 스냅샷**: 내용이 바뀐 회차만 설정한 간격마다(기본 30분), 그리고 회차를 떠날 때(전환, 종료) 마지막 스냅샷과 다르면. 회차당 보관 개수(설정 10~100, 기본 50)를 넘으면 오래된 자동·떠날 때 스냅샷부터 삭제. 수동 스냅샷은 자동으로 지우지 않는다.
- **검색**: 입력한 문구 그대로. 영문 대소문자 구분 안 함이 기본(옵션으로 켬). 줄을 넘는 검색 없음.
- **전체 바꾸기**: 실행 직전 바뀌는 회차 전부 스냅샷. 한 번의 실행 취소로 전부 되돌리기, 어려우면 스냅샷 복원 안내.
- **회차 삭제**: 휴지통으로 못 옮기면 중단하고 알림. 영구 삭제로 대신하지 않는다.
- **내보내기**: 전체는 회차 순서대로 한 파일, 회차마다 "N화 제목" 줄과 빈 줄로 구분. 회차별 파일 옵션.
- **실행 취소**: 회차를 전환하면 기록을 비운다. 전환 때 찍는 스냅샷이 안전망.

구현하려면 정해야 해서 내가 추가로 제안하는 값:

- **자동 저장 지연**: 입력이 멈추고 1초 뒤 저장.
- **저장 재시도**: 0.5초, 1초, 2초 뒤 세 번 다시 시도. 그래도 실패하면 상태 줄에 error 색으로 표시하고 계속 유지.
- **회차 번호**: 파일에 저장하지 않고 목록 순서로 매긴다(1화, 2화…). 순서를 바꾸면 번호도 바뀐다.
- **새 회차 제목**: 비워 두고 사이드바에 inkMuted로 "제목 없음"이라고 보인다.
- **목표 글자 수 기본값**: 새 회차마다 5,000자. 회차별로 바꿀 수 있다. 어느 기준(공백 포함/제외)으로 셀지는 설정을 따른다(결정 사항 3).
- **텍스트 파일 형식**: UTF-8, BOM 없음, 줄바꿈 LF. 내보내기도 같다.
- **외부 변경 감지**: 파일의 수정 시각과 크기로 1차 확인, 다르면 내용을 비교해 실제로 바뀌었는지 판단.
- **스냅샷 파일 이름**: `snapshots/<회차ID>/<시각>-<종류>.md`. 시각은 `20261110-142305` 형식(정렬하면 시간순). 종류는 10장 1번.

- B안(보이는 것만 묶기)이면 묶음 정보는 `project.json`의 목록이라, 지금의 순서 변경 되돌리기와 같은 방식(바꾸기 전 목록 통째로 기록)으로 된다. 파일을 건드리지 않아 안전하다.
- A안(진짜 폴더)이면 파일 옮기기를 되돌려야 해서 휴지통 되돌리기처럼 파일별 기록이 필요하다. B안을 추천하는 이유 중 하나.
- 크기: 작음(묶음 단계 안에 포함).


## 10. 11단계 상세 계획: 버전 스냅샷과 비교

2026-11-12 사용자와 정함. 참고 이미지: [비교 화면](design-snapshots/11-ref-diff.png)(두 칸, 줄 번호, 빨간 빗금·초록 막대), [떠 있는 판](design-snapshots/11-ref-floating-panel.png)(창 위에 뜨는 판, 오른쪽 위 ✕). 미결정이던 11~16번은 2026-11-12 정함(6장).

### 1. 저장 위치와 모양
- 8단계에서 쓰는 자리 그대로: `snapshots/<회차ID>/<시각>-<종류>.md`. 같은 초에 또 찍으면 `-2`, `-3`을 붙이고 이미 있는 파일은 덮지 않는다.
- 종류: `manual`(직접), `auto`(설정한 간격마다, 기본 30분), `leave`(회차를 떠날 때), `restore`(복원 직전 지금 본문), `conflict`·`external`(8단계).
- 목록 파일을 따로 두지 않는다. 폴더의 파일 이름만 읽어 목록을 만든다(본문은 고른 것만 읽음). `project.json`과 형식 버전은 바뀌지 않고, Finder에서 지워도 목록이 어긋나지 않는다.
- 메모: 직접 찍을 때 선택으로 쓴다. 같은 이름의 `<시각>-manual.memo`(일반 텍스트)에 둔다. 본문 파일에 섞으면 복원할 때 메모가 본문에 들어가기 때문이다. `restore`에는 "14:23 버전으로 되돌림" 메모가 저절로 붙는다.
- 코드: NovelCore `Snapshots.swift`(찍기·목록·읽기·메모·정리). 기존 `writeConflictSnapshot`은 이것을 부르게 바꾼다.

### 2. 정리 (보관 개수)
- 메모를 단 것은 종류와 상관없이 세지도 지우지도 않는다(결정 17).
- 회차마다 `auto`와 `leave`만 함께 세서 보관 개수(설정 10~100, 기본 50)를 넘으면 **오래된 것부터 바로 삭제**(휴지통 아님, 사용자 결정).
- 지울 수 있는 종류를 이름 끝으로 고르는 **허용 목록** 방식. `manual`, `restore`, `conflict`, `external`, 모르는 파일은 절대 지우지 않는다. 본문 파일(`episodes/`)은 정리 코드가 아예 보지 않는다.
- 휴지통에 보낸 회차의 스냅샷 폴더는 남긴다(꺼내면 함께 돌아온다).

### 3. 언제 찍나
- 직접(⌃⌘S): 저장을 먼저 끝낸 뒤 지금 본문을 찍고 메모 칸을 띄운다(비워 두고 엔터 가능).
- 자동(기본 30분마다): 지금 회차 본문이 마지막 스냅샷과 다를 때만.
  - **설정 → 일반 → "스냅샷"**(2026-11-12 사용자 요청): `자동 스냅샷` 켜기/끄기(기본 켬), `간격` 5·10·15·30·60분 중 고름(기본 30분), `보관 개수` 10~100 중 10 단위로 고름(기본 50, 자동·떠날 때만 셈). 앱 전체 설정(UserDefaults, 결정 사항 6).
  - 바꾸면 바로 적용: 타이머를 새 간격으로 다시 건다. 끄면 타이머만 멈추고 이미 있는 스냅샷은 그대로. 보관 개수를 낮추면 넘친 오래된 `auto`·`leave`는 다음 정리 때(다음 찍을 때) 지운다.
  - 끄더라도 "떠날 때"와 직접 찍기는 그대로 둔다(되돌아갈 최소한의 안전망). 떠날 때는 끄는 칸을 두지 않는다(결정 16).
- 떠날 때: 회차 전환·창 닫기·앱 종료. 자동 저장이 이미 복사한 본문을 그대로 써서 한 번 더 복사하지 않는다.
- 마지막 스냅샷과 내용이 같으면 건너뛴다. 쓰기는 모두 메인 스레드 밖, 원자적 쓰기. 앱 종료 때는 저장처럼 끝나길 기다린다.

### 4. 비교 엔진 (NovelCore `TextDiff.swift`, 외부 라이브러리 없음)
1. 두 글을 NFC로 맞춘다(다른 편집기가 한글을 자모로 풀어 저장하는 경우).
2. 문단(줄) 단위로 나누고, 앞뒤의 같은 줄을 잘라 가운데만 Swift `difference(from:)`로 비교한다.
3. 붙어 있는 "지운 줄"과 "넣은 줄"을 "고친 줄"로 짝짓는다. 짝지은 줄은 두 칸에서 같은 높이에 놓인다.
4. 고친 줄 안은 바뀐 크기에 맞춰 칠한다(사용자 요청):
   - 줄의 절반 넘게 바뀌면 **문장 단위**: 줄 전체만 칠한다.
   - 아니면 **어절 단위**: 바뀐 어절만 진하게.
   - 어절 안에서 몇 글자만 바뀌면(을→를, 했다→했었다) **글자 단위**: 그 글자만.
   - "절반" 기준은 실제 원고로 비교해 보고 사용자와 정한다.
5. 글자는 `Character` 단위라 한글 음절·이모지가 쪼개지지 않는다.
6. 가운데가 너무 크면 줄 단위 비교만 하고 화면에 알린다(기준은 측정으로 정함). 메인 스레드 밖에서 돌리고, 다른 스냅샷을 고르면 하던 비교는 취소한다.
7. 결과 모양은 화면과 따로 둔다. 나중에 CLI·MCP로 들어올 "고친 기록"도 같은 화면에 넘길 수 있게.

## 11. 메모리 조사와 계획 (2026-11-17)

사용자 요청으로 "메모리가 쌓이는지(새는지), 한 번 늘고 멈추는지"를 가렸다. 자세한 측정 과정은 [log26-11-17.md](log/log26-11-17.md).

### 1. 재는 방법
- `phys_footprint`(활성 상태 보기·perf.sh의 대기 메모리)만 보면 안 된다. 해제한 메모리도 malloc이 운영체제에 바로 돌려주지 않아 한동안 남고, 창 그래픽 버퍼가 섞여 같은 조건에서도 78~112MB를 오간다.
- 그래서 "쌓이는지"는 malloc이 실제로 쥐고 있는 양(`malloc_zone_statistics`의 size_in_use)으로 본다. footprint는 참고값.
- 측정: `Tests/AppTests/MemoryGrowthTests.swift`(perf.sh가 돌림). 사이드바 + 편집 영역(자동 저장기·글자 수·스냅샷 포함)을 띄우고 500회차를 3바퀴 돈 뒤 10만 자 회차를 3번 열고 닫는다. 결과는 perf.sh 표 아래 한 줄.

### 2. 알아낸 것
| 의심 | 결과 |
|---|---|
| 회차를 오가면 본문이 쌓이나 | **아니다.** 편집기·자동 저장기·글자 수만 띄우면 바퀴마다 malloc 변화 0(36.8 → 36.8MB). 떠난 회차 기준을 놓는 수정(`aeb6294`)이 듣고 있다 |
| 10만 자 회차를 열면 27MB 늘던 것 | **한 번만.** 열면 malloc +1.3MB, 떠나면 돌아온다. footprint는 115MB까지 올랐다가 다른 회차로 가면 89MB로 내려온다(글자 배치·그래픽 버퍼) |
| 500회차를 오가면 33 → 74MB | 대부분 **footprint의 빈 칸**. 첫 바퀴 111MB → 다음 바퀴 89MB로 내려온다 |
| 그래도 조금씩 쌓이는 것 | **있다, 아주 작다.** 사이드바 + 편집 영역을 함께 띄우면 회차 전환 한 번에 약 2~3KB(500번에 1.1~1.4MB). 사이드바만 띄워도 1KB쯤. 시스템 `List`만 쓰면 쌓이지 않는다 |
| 쌓이는 것의 정체 | heap·malloc_history로 본 결과 **SwiftUI·AppKit 안쪽 캐시**: 글자 크기 재기 캐시(`CTLine`·`NSCTFont`, SwiftUI `NSAttributedString.MetricsCache`), 화면 모양 객체(`NSCompositeAppearance`), 레이아웃 예약(`_NSActivityAssertion`). 우리 코드가 들고 있는 본문·회차 정보는 없었다 |
| 줄 꾸밈 하나가 원인인가 | 아니다. 회색 칸, 마우스 올림, 접근성 표시, 우클릭 메뉴, 두 번 클릭, 줄 여백을 하나씩 붙여 봐도 각각은 거의 안 쌓인다(바퀴당 0.05~0.14MB). 조합에서 생긴다 |
| 500회차 작품이 1회차보다 13MB 큰 것 | 사이드바 500줄의 SwiftUI 내부 자료(환경 값 2만 개 약 3MB, 줄 특성 1.3MB 등). 화면에 안 보이는 줄도 자료는 만든다 |
| 창을 닫으면 작품 모델이 풀리나 | 풀린다. 릴리스 앱을 띄워 작품 창을 닫은 뒤 heap으로 세면 `ProjectModel`·자동 저장기·편집기가 0개, footprint 99 → 73MB. 여러 번 열고 닫아도 1개를 넘지 않았다. (XCTest 안에서는 시험용 창을 AppKit이 놓지 않아 자동 테스트로 만들지 못했다) |

### 3. 판단
- 실제로 쓰는 양(하루에 회차 전환 수백 번)이면 쌓이는 양은 1MB 안팎이고, 앱을 다시 켜면 없어진다. 원고 유실·끊김과 무관하다.
- 원인이 SwiftUI 안쪽이라 우리 코드를 고쳐 없애려면 사이드바를 AppKit 표(`NSTableView`)로 바꾸는 큰 일이 된다. 지금 하지 않는다.

### 4. 계획 (17단계 마무리 최적화 때)
1. perf.sh의 회차 전환 메모리 줄을 매번 보고, 바퀴당 malloc 증가가 2MB를 넘으면 원인을 다시 찾는다(지금 1.1~1.4MB).
2. 사이드바를 다시 손볼 일이 생기면(회차 묶음 등) 줄 수에 비례하는 SwiftUI 자료를 줄이는 짜임을 함께 본다: 3,000회차 더미로 재고, 필요하면 `NSTableView`로 바꾸는 안을 비교해 먼저 보고한다(보이는 변화가 있을 수 있어 손 확인 필요).
3. 대기 메모리 측정은 창 복원 영향을 없앤다: perf.sh가 메모리를 잴 때 macOS 창 복원을 끈다(`-ApplePersistenceIgnoreState YES`, 2026-11-17 넣음). 전에는 복원된 창이 있으면 77 ↔ 89MB로 흔들렸다.

## 12. 단축키 설정 (2026-11-17 사용자 요청·결정)

스냅샷 찍기(⌥⌘S)가 시스템 사이드바 단축키와 겹친 일을 계기로, 사용자가 단축키를 직접 바꿀 수 있게 한다. 11d와 11e(복원) 사이에 한다(결정 3).

### 결정 (사용자가 추천안을 고름)
1. 눌린 키를 받는 기록기는 AppKit 파일 하나(`App/Settings/ShortcutRecorder.swift`)를 예외로 둔다. SwiftUI만으로는 ⌘ 조합을 메뉴가 먼저 가져간다.
2. 바꿀 수 있는 것은 메뉴 명령만. 사이드바 ↩·↑↓, 판의 Esc 같은 화면 안 키는 그대로.
3. 시기: 지금(11e 전).
4. 스냅샷 찍기 기본값은 ⌃⌘S.

### 화면 (설정 → "단축키", 키보드 아이콘)
- 분류별 목록: 파일(새 작품, 다른 위치에서 열기, 작품 전환, 지금 저장) · 스냅샷(찍기, 보기) · 회차(새 회차, 이전/다음, 이름 변경, 휴지통, 목표 글자 수). 집중 모드·검색·내보내기는 그 기능을 만들 때 표에 한 줄씩 더한다.
- 줄마다 이름과 단축키 칸. 칸을 누르면 "키를 누르세요" → 누른 조합으로 바뀐다. Esc는 취소, ⌫는 단축키 없애기. 바꾼 줄에는 "기본값" 버튼, 맨 아래 "모두 기본값으로".
- 바꾸면 메뉴에 바로 반영되고 다음 실행에도 남는다(앱 전체 설정, UserDefaults).

### 규칙
- ⌘가 들어가야 한다(⌘ 없는 조합은 글쓰기를 막는다).
- 시스템·편집 표준 단축키는 고를 수 없고 이유를 보여 준다: ⌘Q, ⌘W, ⌥⌘W, ⌘H, ⌥⌘H, ⌘M, ⌘,, ⌘?, ⌘C/V/X/A, ⌘Z/⇧⌘Z, ⌥⌘S(사이드바), ⌘⌫, ⌘←→↑↓, ⌘` 등.
- 앱 단축키끼리 겹치면 "‘…’이(가) 이미 쓰고 있어요" → 바꾸면 상대 항목은 단축키가 비고, 취소하면 그대로.
- 한글 입력 중에 눌러도 글자("ㄴ")가 아니라 키 위치(키 코드)로 읽어 "S"로 기록한다.
- 휴지통: 기본값일 때는 지금처럼 사이드바에 초점이 있으면 ⌘⌫, 편집기에서는 ⌥⌘⌫. 사용자가 바꾸면 어디서나 그 조합.

### 짜임
- `App/Shortcuts/`: `KeyCombo`(키 + 보조키, 저장 문자열, 표시 문자열 ⌃⌥⇧⌘), `ShortcutCommand`(명령 목록·분류·이름·기본값, 한 곳), `ShortcutSettings`(바꾼 것만 담는 표, 겹침·막힌 조합 판정).
- 저장: UserDefaults 키 하나(`shortcuts`)에 바꾼 것만 문자열로. 메뉴(`ProjectCommands`, `EpisodeCommands`)와 설정 창이 `@AppStorage`로 같이 읽는다.
- 글쓰기 경로(키 입력·저장)는 건드리지 않는다. 메뉴는 설정이 바뀔 때만 다시 계산된다.

### 테스트
- 기본 표에 겹침이 없고 막힌 조합이 없다. 저장 문자열 왕복. 겹침·막힘 판정. 휴지통 사이드바 규칙.
- 키 코드 → 키(한글 입력과 무관). 바꾼 단축키가 실제 메뉴 항목에 반영된다(`FileMenuTests` 확장).
- 디자인 스냅샷 `settings-shortcuts`.

## 13. 12단계 작품 전체 검색 (2026-11-20 사용자 결정)

- **여는 법**: 편집 메뉴 `작품 전체 검색`(⇧⌘F, 단축키 설정에서 바꿀 수 있음). 사이드바 자리가 검색 패널로 바뀐다(DESIGN 6장). Esc나 ✕로 회차 목록에 돌아간다.
- **언제 찾나**: 입력이 **0.2초 멈추면** 바로 찾는다(사용자 결정). 새로 치면 하던 검색은 취소한다.
- **무엇을**: 입력한 문구 그대로, 문단(엔터) 안에서만. 영문 대소문자 구분은 끔이 기본, 패널의 `Aa`로 켠다. 한글은 자모를 따로 적은 글(NFD)도 같은 글자로 찾는다.
- **어떤 본문을**: 열린 회차는 편집기의 지금 글, 저장에 실패해 메모리에만 있는 회차는 그 글, 나머지는 디스크 파일. 못 읽은 회차는 결과 아래에 따로 알린다.
- **결과**: 회차별로 묶어 `3화 제목 (4)`, 줄마다 `줄 번호 + 줄 미리 보기`(일치 부분 accent 18% 배경, 긴 줄은 앞뒤를 잘라 `…`). 결과가 1,000개를 넘으면 앞 1,000개만 보이고 그렇다고 알린다.
- **누르면**: 그 회차로 옮기고 일치한 곳을 선택해 가운데로 스크롤, 편집기에 초점. 그사이 글이 바뀌어 그 자리에 문구가 없으면 가장 가까운 같은 문구로 간다.
- **나누기**: NovelCore `TextSearch`(한 본문에서 찾기, 줄 번호·미리 보기)와 `ProjectStore.search`(여러 회차, 취소 가능) → 앱 `ProjectSearch`(0.2초 기다림, 열린 회차 글 넘기기) → `SearchPanel`(화면) → 편집기 `reveal`.
- **측정**: 500회차 전체 검색, 처음과 두 번째(SPEC 8장 목표 0.5초). 메인 스레드는 막지 않는다.
- **테스트**: 대소문자, NFC/NFD, `\r\n` 줄 번호, 한 줄에 여러 번, 줄을 넘는 문구 없음, 1,000개 자르기, 열린 회차의 저장 안 된 글을 찾음, 못 읽은 회차, 바뀐 글에서 누르기.

## 14. 13단계 상세 계획: 전체 바꾸기 (2026-11-22 사용자 결정)

모습은 `build/mockups/replace-and-rename.html`(git 밖, 예시)로 함께 봤다. 이 장이 9장 4번보다 앞선다.

### 1. 화면
- 검색 패널의 찾기 칸 아래에 **바꿀 말** 칸과 `모두 바꾸기` 버튼. 바꿀 말은 비워도 된다(지우기). 줄바꿈은 넣을 수 없다(찾기와 같은 규칙).
- 바꿀 말을 치는 동안 결과 줄마다 `찾은 말`(지운 줄 색, 취소선)과 `바꿀 말`(넣은 줄 색)을 바로 보여 준다(VS Code 검색 바꾸기와 같음).
- 찾은 말과 바꿀 말이 같거나 찾은 곳이 없으면 버튼이 흐리다. 하나씩 바꾸기는 만들지 않는다(사용자 결정).

### 2. 실행 순서 (2026-11-22 사용자 결정: "웬만해서는 바뀌게", 글쓰기가 끊기지 않게)
1. 버튼을 누르면 메인 스레드 밖에서 **끝까지 다시 센다**(검색 결과는 1,000곳에서 잘리므로).
2. 확인 창: `37개 회차에서 412곳을 '도윤'(으)로 바꿀까요?` + "바꾸기 전 글은 회차마다 스냅샷으로 남겨요". 바꿀 말이 비면 `37개 회차에서 '민준' 412곳을 지울까요?`. 문구는 VS Code의 같은 창(`Replace {0} occurrences across {1} files with '{2}'?`)을 따른다.
3. 확인한 뒤 회차마다 **바꾸는 순간의 지금 글에서 다시 찾아** 바꾼다. 센 때와 글이 달라도 건너뛰지 않는다(작가가 바꾸겠다고 했으므로). 숫자는 확인 창과 한두 곳 다를 수 있고, 토스트는 실제로 바꾼 수를 보인다.
   - 회차마다 `바꾸기 전`(종류 `replace`) → 바꾸기 → `바꾼 뒤`(종류 `replaced`) 스냅샷. 한 번의 바꾸기에서 나온 스냅샷은 모두 같은 시각. 메모 `'민준' → '도윤' 전체 바꾸기 · 바꾸기 전 · 12곳` / `… · 바꾼 뒤 · 12곳`(지우기는 `'민준' 모두 지우기 · …`). 두 종류 모두 보관 개수로 지우지 않는다. 확인 창에서 취소하면 아무것도 남기지 않는다.
   - `바꾸기 전`을 남기지 못한 회차는 바꾸지 않는다. `바꾼 뒤`를 못 남긴 것은 바꾸기를 막지 않는다.
4. 회차마다 바꾸기
   - 열린 회차: **맨 마지막에**. 한글 조합 중이면 조합이 끝날 때까지 기다렸다가, 끝난 그 순간 지금 글에서 찾은 자리만 바꾼다(본문 통째로 갈지 않음). 커서는 같은 글자 자리, 화면은 움직이지 않고, ⌘Z 한 번으로 돌아간다.
   - 나머지: 파일을 새로 읽거나(앱 밖에서 바뀌었으면 바뀐 글에서) 저장 실패로 메모리에만 있는 글에서 바꾸고, 그 글을 읽은 상태를 기준으로 조건부로 쓴다. 읽고 쓰는 사이에 또 바뀌면 다시 읽어 3번까지.
   - 건너뜀은 둘뿐: 외부 변경 충돌을 아직 고르지 않은 회차, `바꾸기 전` 스냅샷을 못 남긴 회차(그리고 3번 모두 엇갈린 회차). 센 뒤 휴지통으로 간 회차는 바꾸지 않되 건너뜀으로 세지 않는다.
   - 쓰기를 끝내 실패하면 평소 저장 실패처럼 메모리에 붙잡고 상태 줄이 알린다(바꾼 것으로 센다).
5. 끝나면 사이드바 글자 수를 다시 세고 토스트. 0인 항목은 띄우지 않는다: `412곳을 바꿨어요`, `412곳을 바꿨어요 · 1개 회차는 건너뛰었어요`, 하나도 못 바꾸면 `바꾼 곳이 없어요 · …`. 검색 패널은 **바꾼 회차 목록**으로 바뀐다(③). 토스트의 `되돌리기`·`바꾼 곳 보기`는 ③·④.

### 3. 바꾼 회차 목록 (2026-11-22 사용자 결정)
- 줄 하나 = `5화 제목 · 12곳`. 누르면 그 회차로 가서 스냅샷 판이 **`바꾸기 전`을 골라 둔 채** 열린다. 판은 "처음 고를 스냅샷"만 받으면 된다.
- 검색어를 고치거나 패널을 닫을 때까지 남는다. 토스트의 `바꾼 곳 보기`도 첫 회차로 같은 일을 한다.

### 4. 나누기
- NovelCore: `TextReplace`(한 본문에서 바꾸기: 검색과 같은 일치 규칙, 뒤에서부터 바꿔 자리가 밀리지 않게), `ProjectStore.replacementPlan`(여러 회차 개수 세기, 취소 가능), `SnapshotKind.replace`.
- 앱: `ProjectReplace`(실행·되돌리기 기록), `SearchPanel`(바꿀 말 칸·미리 보기·바꾼 회차 목록), `EpisodeAutosaver`에 "열리지 않은 회차 본문을 바꿔 저장 줄에 넣기", `SnapshotPanel`에 처음 고를 스냅샷.

### 5. 되돌리기 (2026-11-22 사용자 결정: 실수해도 번거롭지 않게, 고른 회차만)
VS Code는 여러 파일 되돌리기를 `Undo in {0} Files`·`Undo this File`로 묻고, 그 뒤 고친 파일이 있으면 멈춘다. 글쓰기 흐름이 우선이라 다르게 간다.
- **편집기의 ⌘Z**: 묻지 않고 그 회차만 되돌린다(⇧⌘Z로 다시). 토스트 `이 회차만 되돌렸어요 · 모든 회차 되돌리기`.
- **되돌리기 창**(두 회차 이상 바꾼 작업): 토스트 `되돌리기`, 편집 메뉴 `전체 바꾸기 되돌리기…`, 사이드바·검색 패널의 ⌘Z가 연다. 한 회차만 바꾼 작업은 창 없이 바로 되돌리고 `다시 바꾸기` 토스트.
  - 제목 `'민준' → '도윤' 전체 바꾸기 되돌리기`, 아래 `오늘 15:02에 37개 회차, 412곳을 바꿨어요.`
  - 목록은 **지금 되돌리면 실제로 바뀌는 곳이 남은 회차만**(열 때 다시 감지). 이미 되돌렸거나 바꾼 자리를 모두 고친 회차는 빼고 `2개 회차는 이미 되돌려서 목록에 없어요.`
  - 줄 = 체크 칸 + `3화 제목` + `12곳` + (바꾼 뒤 고쳤으면) `그 뒤에 고침 (1곳은 그대로)`. **기본은 모두 선택.** 체크·⇧클릭 범위·⌘클릭·스페이스, `모두 선택`/`모두 해제`.
  - 회차를 누르면 오른쪽에 `지금 → 되돌린 뒤` 비교(스냅샷 판의 `DiffView`).
  - 버튼 `취소` / `N개 회차 되돌리기`(0개면 흐림). 고르지 않은 회차는 파일도 편집기도 건드리지 않고, 기록에 남아 다음에 창을 열면 그 회차만 보인다.
- **바꾼 자리만 되돌린다**: 회차를 `바꾸기 전` 글로 통째로 덮지 않는다. `바꾸기 전`·`바꾼 뒤` 스냅샷으로 바꾼 자리를 알아내 지금 글에서 그 자리를 찾아(NovelCore에 글자 위치 따라가기 함수를 새로) 원래 말로 돌린다. 원래 있던 같은 말과 그 뒤에 쓴 글은 그대로, 작가가 손댄 바꾼 자리는 그대로 두고 `1곳은 그 뒤에 고쳐서 그대로 뒀어요`. 메모리에는 본문을 들지 않는다.
- **되돌리기 전 스냅샷**: 되돌리는 회차마다 지금 글을 새 종류 `되돌리기 전`으로 먼저 남긴다(못 남기면 그 회차는 되돌리지 않음). 메모 `'민준' → '도윤' 전체 바꾸기(11월 22일 15:02) 되돌림 · 12곳`, 그대로 둔 곳이 있으면 `… · 7곳, 1곳은 그 뒤에 고쳐 그대로`.
- **다시 바꾸기**: 끝나면 토스트 `2개 회차를 되돌렸어요 · 다시 바꾸기`(방금 되돌린 회차만, 같은 방식, `바꾸기 전` 스냅샷과 메모 `'민준' → '도윤' 다시 바꾸기 · 12곳`). 편집 메뉴에도 `다시 실행`.
- 여러 번 바꿨으면 최근 것부터. 되돌리기 버튼이 있는 큰 작업의 토스트는 5초쯤 띄운다.
- 쓰기는 바꾸기와 같은 길(저장 줄, 조건부 쓰기, 열린 회차는 조합이 끝난 뒤 찾은 자리만).

### 6. 테스트와 측정
- NovelCore: 일치 규칙이 검색과 같음(대소문자, NFC/NFD, 이모지 경계, 한 줄 여러 곳, 빈 바꿀 말), 개수 세기와 잘림 없음, 취소.

- 측정: 더미 500화 모두 바꾸기(미결정 20).

## 15. 여러 회차 이름 바꾸기 (13-1, 2026-11-22 사용자 결정)

- **여는 법**: 사이드바에서 ⌘클릭·⇧클릭으로 여러 회차를 고르고 우클릭 `N개 회차 이름 변경…`. 하나만 골랐으면 지금 이름 변경 그대로.
- **창 대신 사이드바에서 바로**(사용자 결정): 사이드바 맨 위가 입력 줄로 바뀐다. 방식 세 가지(Finder의 여러 파일 이름 바꾸기와 같음) — `글자 바꾸기`(찾을 말 → 바꿀 말), `앞·뒤에 붙이기`, `새 이름 + 번호`(시작 번호, 번호 자리 앞/뒤). 칸이 많은 방식은 두 줄로 쌓는다(사이드바 폭 240pt).
- 치는 동안 고른 회차 줄이 **그 자리에서 바뀐 이름**(진하게)과 옛 이름(아래 흐린 취소선)을 보여 준다. 엔터 전까지는 미리 보기일 뿐이라 `project.json`에 쓰지 않는다. Esc면 아무것도 안 바뀐다.
- 엔터: 바뀌는 이름이 있을 때만 적용, `replaceEpisodes` 한 번이라 ⌘Z 한 번에 되돌아간다. 토스트 `3개 회차 이름을 바꿨어요 · 되돌리기`.
- **한글 함정**: 조합 중 엔터는 마지막 글자가 빠진 값으로 적용될 수 있다. 엔터는 조합이 끝난 다음 차례에 적용하고 테스트·한글 체크리스트에 넣는다.
- 나누기: NovelCore `EpisodeTitleBatch`(순수 함수: 방식 + 입력 + 제목 목록 → 새 제목 목록) 단위 테스트. 앱은 `EpisodeList` 위 입력 줄과 줄 미리 보기.

## 16. 같은 말 여러 커서 (13-2, ⌘D, 2026-11-22 사용자 요청)

사용자 원칙: **사용자 경험을 해치는 방식은 쓰지 않는다. VS Code와 같은 경험.** 그래서 "다른 자리는 한 단어 늦게 따라오기"안은 버렸다.

### 1. VS Code가 하는 방법 (설치된 VS Code 1.147 `workbench.desktop.main.js`를 읽어 확인, 2026-11-22)
REA의 전체 분석은 압축된 파일을 문법 분석하지 못했다(parse failure 1). 같은 파일에서 해당 코드를 직접 찾아 읽었다. 실행해 본 것은 아니다.
- 입력기는 문서가 아니라 **첫 커서 자리에 숨긴 입력 칸**과 이야기한다(`_textAreaInput.onType`).
- 조합이 바뀔 때마다 입력 칸의 변화를 "앞 N글자를 이 글로"(`text`, `replacePrevCharCnt`)로 바꿔 **모든 커서에서 문서를 실제로 고친다**(`getEdits` 안 `selections.map(_compositionType)`). 그래서 모든 자리에 동시에 쳐진다.
- 조합 시작 때 커서들을 기록하고 끝날 때 결과를 계산한다(`startComposition`, `deduceOutcome`). 조합 하나가 실행 취소 한 단위.
- ⌘D: 커서만 있으면 커서 아래 단어를 **단어 전체·대소문자 구분**으로 고르고, 다음부터는 마지막 선택 뒤에서 다음 일치를 찾아 더한다. 커서 수 한도 기본 10,000개(넘으면 알림).

### 2. 우리 편집기에 옮기는 방법
- **여러 커서일 때만** `ManuscriptTextView`가 입력기와의 약속(`NSTextInputClient`: `setMarkedText`, `insertText`, `unmarkText`, `markedRange`, `hasMarkedText`, 후보 창 위치 `firstRect`)을 직접 맡는다. VS Code의 숨긴 입력 칸 역할.
- 조합이 바뀔 때마다 모든 자리를 뒤에서부터 실제로 고치고, 첫 자리의 조합 범위는 우리가 다시 계산해 입력기에 알린다. 조합 밑줄은 본문을 건드리지 않는 임시 속성으로 그린다.
- **커서가 하나면 지금 코드 그대로.** 평소 입력에는 위험이 늘지 않는다.
- 범위: 지금 회차 안. 화살표·클릭은 모든 커서를 같이 옮긴다. Esc는 커서 하나로. 실행 취소는 조합 하나를 한 단위로.

### 3. 규칙 예외 (미결정 22)
"조합 중에는 텍스트 저장소를 고치지 않는다"는 `NSTextView`가 속으로 들고 있는 조합 범위가 어긋나는 것을 막는 규칙이다. 여러 커서 상태에서는 조합 범위를 우리가 들고 있으므로 이유가 사라진다. 실험이 통과하면 근거와 함께 CLAUDE.md에 예외로 적고 허락을 받는다.

### 5. 실험 결과 (2026-11-22, macOS 27.3, 두벌식)
`build/ime-lab/`의 작은 실험 편집기(TextKit 1 `NSTextView` + 여러 커서)에 실제 키 코드를 보내(HID 이벤트, 컴퓨터 유스 전체 화면 제어) 입력기 호출을 기록했다. 컴퓨터 유스의 `type`·`key`는 입력기를 거치지 않거나 키 코드가 0이라 쓸 수 없었다.

**입력기가 하는 일 (관찰)**
- 두벌식 입력기는 **두 방식**을 쓴다. ⓐ 바꾸기 방식: 표시된 글자 없이 `insertText("도", replacementRange: 커서 앞 1글자)`. 새 앱의 처음 방식이다. ⓑ 표시된 글자 방식: `setMarkedText("도")` → 확정 때 `insertText`.
- 입력기는 **앱(번들 ID)마다 방식을 기억**한다. ⓐ에서 위치가 맞지 않는 일이 한 번 생기자 그 앱은 ⓑ로 바뀌어 다시 켜도 그대로였다(새 번들 ID는 다시 ⓐ). 그래서 **두 방식 모두 처리**해야 한다.
- ⓐ에서 입력기는 자기가 넣은 글자 위치를 기억해 두고, **같은 키 이벤트 안에서는 다시 묻지 않는다**. 다른 자리를 고쳐 그 앞 위치가 밀리면 다음 키에서 어긋난 위치를 준다. 이벤트 사이의 변경(본문 앞에 글자 넣기)은 다시 물어 맞춘다.
- 커서를 옮기면(프로그램·화살표) 입력기는 조합을 끝낸다. `discardMarkedText()`도 끝낸다. 본문을 통째로 바꿔도 커서가 다시 놓이므로 조합이 이어지지 않는다.

**여러 커서 결과**
- 세 자리 `민준` → `도윤 `: ⓐ·ⓑ 둘 다 세 자리에 동시에 들어갔다(`동`→`도유`로 떨어지는 움직임까지 같음).
- 빠르게(키 간격 약 11ms) 24키: 세 자리 모두 같고 어긋남 0.
- 조합 중 지우기(`동`→`도`→`ㄷ`→빈칸), 확정 뒤 지우기, 엔터: 모든 자리에서 같게.

**실험에서 잡은 버그와 고친 법 (설계에 반영)**
- ⓑ에서 확정(`insertText`)을 표시된 범위가 아닌 커서 자리에 넣어 **글자가 두 번** 들어갔다 → 확정은 늘 표시된 범위를 바꾼다.
- 주 커서가 뒤쪽이면 ⓐ에서 앞 자리를 고칠 때 입력기의 기억 위치가 밀려 어긋났다(실험 앱은 어긋남을 알아채고 여러 커서를 끝내 글은 안전) → **입력기와 이어진 커서는 늘 맨 앞 커서**로 둔다. 화면을 따라가는 커서는 따로 둘 수 있다.
- 입력기가 준 범위가 맨 앞 커서 둘레가 아니면 여러 커서를 끝내고 보통 입력으로 넘긴다(이 안전한 물러남은 실제로 동작했다).

**2번 설계에서 바뀐 것**
- 입력기 연산은 VS Code와 같은 "커서 앞 N글자, 뒤 M글자를 이 글로"로 정규화한다(ⓐ의 `replacementRange`를 맨 앞 커서 기준 상대값으로 바꿔 모든 자리에). ⓑ는 자리마다 표시된 범위를 들고 있는다.
- 3번 규칙 예외는 ⓑ에서만 필요하다(ⓐ에는 표시된 글자가 없음).

**알게 된 것 (지금 앱)**
- ⓐ에서는 `hasMarkedText()`가 늘 false라, 지금 앱의 "조합 중이면 미루기" 코드(`applyStyle`, `didChangeText`의 실행 취소 끊기)가 한글에서는 동작하지 않는다. 본문을 통째로 바꾸는 길은 커서가 다시 놓여 안전했다. **실행 취소 단위**: 실제 앱에서 "도윤 가가" 뒤 ⌘Z가 조합 중간 글자 "각"을 보여 줬다 → 2026-11-22 고침(입력기가 넣는 한 글자를 편집기가 직접 한 단위로 기록, `ManuscriptTextView.insertText`).
- 실제 키 코드를 보내면 진짜 입력기가 돈다 → 검증 스킬의 "한글 조합은 재현할 수 없음" 한계를 풀 수 있다.

**시험하지 못한 것**: 세벌식·다른 회사 입력기(이 맥에 없고, 입력 소스 추가는 시스템 설정 변경이라 하지 않음), 받아쓰기, 이모지 창, 한자 변환, 실행 취소 묶음, 화살표로 모든 커서 옮기기.

## 17. VS Code에서 배울 원고 안전 장치 (2026-11-22 조사)

### 이미 VS Code보다 강한 것
- **원자적 쓰기 + 디스크 내려 쓰기**: VS Code는 설정 파일 같은 일부만 임시 파일(`.vsctmp`)로 원자적으로 쓰고, 일반 파일은 그 자리에 쓴다. 우리는 본문·`project.json`·스냅샷 모두 원자적 쓰기 + `F_FULLFSYNC`.
- **저장 충돌**: VS Code 기본 `askUser`(비교 또는 덮어쓰기). 우리는 앱 쪽을 스냅샷으로 먼저 남기고 묻는다.
- **밖에서 지운 파일**: VS Code는 편집기를 닫지 않고 내용을 지킨다(`closeOnFileDelete` 기본 끔). 우리는 저장할 때 앱의 내용으로 다시 만든다.
- **늦은 저장 막기**: 변경 번호와 저장 줄. VS Code의 백업도 내용 버전을 확인한다(`hasBackupSync(r, version)`).

### VS Code에 있지만 들이지 않을 것
- `Compare with Saved`·`Revert File`: 1초 자동 저장이라 디스크와 편집기가 거의 같다. 스냅샷 비교가 같은 일을 한다.
- 저장 충돌 `overwriteFileOnDisk`(묻지 않고 덮어쓰기): 원고 유실 위험.
- 관리자 권한으로 다시 저장(`Retry as Sudo`): 작품 폴더는 사용자 폴더라 필요 없다.
