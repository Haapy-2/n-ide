# 소설 집필 에디터 (macOS 네이티브) 개발 지시서

너는 이 저장소에서 macOS용 소설 집필 에디터를 처음부터 만든다. 아래 내용을 끝까지 읽고, "작업 방식"에 적힌 순서대로 진행해라.

## 1. 배경

- 나는 대학교 1학년이고 Swift와 macOS 개발은 처음이다. 이 앱은 우선 나 혼자 쓰려고 만든다.
- 한국어 웹소설을 쓴다. 회차 하나가 대략 5,000자이고, 한 작품이 수백 회차까지 늘어난다.
- 이 프로젝트의 우선순위는 아래 순서다. 둘이 충돌하면 위에 있는 것을 택하고, 그 사실을 나에게 알려라.
  1. **내가 보기 편하고 관리하기 편할 것.** 이것이 1원칙이다. 폴더를 열었을 때 무엇이 어디 있는지, 지금 어디까지 됐는지, 어떻게 실행하는지를 내가 바로 알 수 있어야 한다. 구체적인 규칙은 4장에 있다.
  2. **최적화.** 빠르고 가볍고 한글 입력이 절대 깨지지 않을 것.
  3. **깔끔한 디자인.**
  4. **탄탄한 기능.** 기능 수를 늘리는 것보다 있는 기능이 확실히 동작하는 것이 중요하다.
- 나중에 아이패드, 아이폰 버전을 추가할 수 있다. 지금 만들지는 않지만 그때 다시 짜지 않도록 구조를 잡아야 한다.

## 2. 개발 환경

- 기기: MacBook Air M2, 메모리 8GB. 메모리가 작으니 빌드나 테스트를 여러 개 동시에 돌리지 마라.
- 시작하기 전에 `sw_vers`와 `xcodebuild -version`으로 macOS와 Xcode 버전을 확인하고, 그 버전에 맞춰 최소 지원 버전과 Swift 버전을 정해라. Xcode가 없거나 명령줄 도구만 있으면 작업을 멈추고 나에게 알려라.
- 새 도구(Homebrew 패키지 등)를 설치해야 하면 설치하기 전에 무엇을 왜 설치하는지 말하고 내 허락을 받아라.

## 3. 기술 결정 (확정, 바꾸지 말 것)

| 항목 | 결정 |
|---|---|
| 언어 | Swift |
| 화면 틀 | SwiftUI (사이드바, 설정, 창 구성) |
| 편집기 | AppKit `NSTextView`를 `NSViewRepresentable`로 감싼다. TextKit 1을 명시적으로 사용한다. |
| 저장 | 일반 파일. 회차마다 `.md` 파일 하나, 작품 정보는 `project.json` |
| 외부 라이브러리 | 사용하지 않는다. Apple 기본 프레임워크만 쓴다. (예외: 5장의 글꼴 파일) |
| 데이터베이스 | 사용하지 않는다. |

이 결정 중 하나가 성능 목표 달성을 막는다고 판단되면, 임의로 바꾸지 말고 근거와 함께 나에게 먼저 제안해라.

### 구조 요구사항

- 코드를 두 덩어리로 나눈다.
  - `NovelCore`: 데이터 모델, 파일 읽기와 쓰기, 검색, 글자 수 계산, 스냅샷. AppKit과 SwiftUI를 import하지 않는다. Foundation만 쓴다. 로컬 Swift 패키지로 만든다.
  - 앱 타깃: 화면과 편집기. AppKit 코드는 편집기 관련 파일 안에만 둔다.
- `NovelCore`는 나중에 iOS 타깃에서 그대로 가져다 쓸 수 있어야 한다. 그래서 macOS 전용 API를 쓰지 않고, 작품 폴더 위치 같은 경로는 밖에서 넘겨받는다. 편집기 화면은 iOS에서 새로 만드는 것이 전제이니 재사용 대상이 아니다.
- 프로젝트 생성 방식(Xcode 프로젝트 파일을 어떻게 만들지)은 네가 정해라. 조건은 두 가지다. 터미널에서 `xcodebuild`로 빌드와 테스트가 되어야 하고, 내가 Xcode에서 열어 실행 버튼으로 돌릴 수 있어야 한다.

## 4. 프로젝트 관리

1원칙(내가 보기 편하고 관리하기 편할 것)을 지키기 위한 규칙이다. 나는 이 폴더를 Claude Code 프로젝트로 등록해 계속 관리하고, GitHub에 올려 가며 작업한다.

### 한 폴더 원칙

- 저장소 루트 폴더 하나가 곧 Claude Code 프로젝트 폴더이자 GitHub 저장소다. 코드, 에셋, 글꼴, 문서, 스크립트, 빌드 산출물까지 이 프로젝트가 만드는 모든 파일은 이 폴더 안에 둔다.
- 이 폴더 밖에는 파일을 만들지 않는다. Xcode처럼 맥에 따로 설치되는 도구와 그 도구 자체의 캐시만 예외다.
- 터미널에서 빌드할 때는 산출물이 폴더 안 `build/`에 모이도록 한다(`xcodebuild -derivedDataPath build/DerivedData`). 홈 폴더 쪽에 빌드 결과가 흩어지지 않게 해라.
- 성능 측정용 더미 작품, 임시 파일도 `build/` 아래에 만든다. `build/`는 통째로 지워도 문제없어야 한다.
- 내가 실제로 쓰는 원고(`.novel` 폴더)는 이 저장소에 넣지 않는다. 코드 저장소와 원고는 분리한다.

### 폴더 구조

아래 구조로 시작한다. 더 나은 안이 있으면 계획 단계에서 제안하되, "루트가 한눈에 들어온다"는 조건은 지켜라.

```
NovelEditor/                 저장소 루트 (Claude Code 프로젝트 폴더)
  README.md                  이 프로젝트가 무엇이고, 어떻게 빌드하고 실행하는지, 폴더 지도
  CLAUDE.md                  Claude Code가 세션마다 자동으로 읽는 핵심 규칙 요약
  NovelEditor.xcodeproj      Xcode 프로젝트 (만드는 방식에 따라 이름과 형태는 달라질 수 있음)
  App/                       앱 소스 (화면, 편집기)
    Resources/               글꼴, 아이콘, 색 등 에셋
  Packages/
    NovelCore/               공통 로직 패키지와 그 테스트
  Tests/                     앱 쪽 테스트, 성능 테스트
  Scripts/                   build.sh, test.sh, run.sh, perf.sh 등
  docs/                      SPEC.md, PLAN.md, DESIGN.md, PROGRESS.md, 체크리스트, design-snapshots/
  build/                     빌드 산출물과 임시 파일 (git에 올리지 않음)
  .gitignore
```

- 루트에는 위에 적힌 항목만 둔다. 루트에 새 파일이나 새 최상위 폴더를 추가하려면 먼저 이유를 말하고 내 허락을 받아라.
- 문서는 전부 `docs/`에 둔다. 이 지시서에서 `PLAN.md`, `DESIGN.md`처럼 파일 이름만 적은 문서도 모두 `docs/` 아래를 뜻한다. 예외는 루트의 `README.md`와 `CLAUDE.md` 둘뿐이다.
- 쓰지 않는 파일, 빈 폴더, 실험하다 남은 코드, 백업 사본(`파일 2.swift`, `old_` 같은 것)을 남기지 않는다. 단계를 끝낼 때마다 정리해라.
- 파일과 폴더 이름만 보고 역할을 알 수 있게 짓는다.
- 구조가 바뀌면 같은 커밋에서 `README.md`와 `CLAUDE.md`의 폴더 지도도 고친다.

### 내가 읽는 문서

- `README.md`: 한 화면 분량. 프로젝트 소개 두세 줄, 빌드와 실행 방법, 폴더 지도, 문서 목록.
- `docs/PROGRESS.md`: 지금 어디까지 됐는지 한눈에 보는 문서. 끝난 단계, 진행 중인 단계, 다음 할 일, 알려진 문제, 최근 성능 측정 표. 단계가 끝날 때마다 갱신한다.
- `docs/SPEC.md`: 이 지시서 원문을 그대로 저장한다. 요구사항이 바뀌면 내가 말한 내용을 여기에 반영한다.
- `CLAUDE.md`: Claude Code가 세션을 시작할 때마다 자동으로 읽는 파일이다. 200줄 이내로 짧게 유지하고, 다음만 담는다. 우선순위 네 가지, 폴더 지도, 빌드·테스트·실행 명령, 코드 규칙, 하면 안 되는 것, 자세한 내용이 있는 `docs/` 문서 위치. 세부 사양을 여기에 복사하지 말고 `docs/`를 가리켜라.

### 한 줄 명령

내가 외울 필요 없이 `Scripts/`의 스크립트 하나로 실행되게 해라.

- `Scripts/build.sh`: 빌드
- `Scripts/run.sh`: 빌드하고 앱 실행
- `Scripts/test.sh`: 테스트 전체
- `Scripts/perf.sh`: 성능 측정을 돌리고 결과 표 출력

각 스크립트는 짧게 유지하고, 맨 위에 무엇을 하는지 한 줄 주석을 단다.

### git과 GitHub

- 첫 단계에서 `git init`을 하고 `.gitignore`를 만든다. `build/`, `.DS_Store`, `xcuserdata/`, `CLAUDE.local.md`는 올리지 않는다.
- 커밋은 작은 단위로 자주 한다. 메시지는 한국어로, 무엇을 왜 바꿨는지 한 줄로 쓴다.
- 브랜치는 `main` 하나로 단순하게 간다. 강제 푸시와 히스토리 다시 쓰기는 하지 않는다.
- GitHub 저장소는 비공개로 만든다. 원격 저장소를 만들거나 연결하기 전에 나에게 먼저 물어라. `gh`가 설치되어 있고 로그인되어 있는지 확인하고, 아니면 내가 할 일을 순서대로 알려줘라.
- 원격이 연결된 뒤에는 단계가 끝나고 내가 승인할 때마다 푸시한다.
- 비밀번호, 토큰, 개인 정보는 커밋하지 않는다.

## 5. 디자인

디자인은 기능만큼 중요하다. 네가 평소에 기본으로 만드는 모양(둥근 카드, 그림자, 그라데이션, 여러 개의 강조색, 아이콘 남발, 의미 없는 장식)을 쓰지 마라. 아래 방향과 값을 따르고, 여기 없는 결정은 이 방향에 맞게 네가 정하되 `DESIGN.md`에 기록해라.

### 방향: "잘 만든 종이 원고"

- 화면의 주인공은 글이다. 첫인상은 앱이 아니라 깨끗한 종이 한 장이어야 한다.
- 장식이 아니라 타이포그래피, 여백, 정렬로 완성도를 만든다.
- 글을 쓰는 동안에는 본문 외의 요소가 거의 보이지 않아야 한다.
- 맥 앱다운 느낌을 유지한다. 사이드바, 툴바, 메뉴, 설정 창은 시스템 표준 컨트롤과 재질을 쓰고, 개성은 편집 영역과 색, 글꼴에서 낸다. 시스템 컨트롤을 흉내 낸 가짜 컨트롤을 만들지 마라.
- (2026-11-10 추가) Apple의 리퀴드 글래스(Liquid Glass) 디자인을 적용한다. 적용 방식은 `DESIGN.md`에 정리한다.

### 색

색은 아래 토큰으로만 쓴다. 코드에 색 값을 흩어 놓지 말고 한 파일에서 관리한다.

| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| paper | #F8F6F1 | #1C1B19 | 편집 영역 배경 |
| ink | #1F1E1C | #E4E0D8 | 본문 글자 |
| inkMuted | #6F6A62 | #958F86 | 글자 수, 보조 정보 |
| sidebar | #F1EEE8 | #242320 | 사이드바 배경 (시스템 재질을 쓸 수 없을 때의 기준값) |
| rule | #E6E2DA | #2C2A27 | 구분선 |
| error | #C4302B | #F07A70 | 저장 실패 등 경고 글자 |
| accent | #3E5C76 | #8FA9C2 | 선택, 커서, 진행률. 화면에 한두 군데만 |
| selection | accent 18% 투명도 | accent 28% 투명도 | 선택 영역 |

- 순수한 흰색(#FFFFFF)과 순수한 검정(#000000)은 쓰지 않는다. 눈이 덜 피로하도록 살짝 따뜻한 톤을 쓴다.
- 강조색은 하나뿐이다. 경고(저장 실패, 삭제 확인 등)만 error 토큰을 쓴다. 시스템 빨강은 종이색 배경에서 글자 대비가 부족해 더 어둡게 잡았다.
- 다크 모드는 라이트 모드를 반전한 것이 아니라 따로 다듬은 것이어야 한다.
- 위 색 값은 출발점이다. 실제 화면에서 대비가 부족하거나 어색하면 조정하고, 바꾼 이유를 `DESIGN.md`에 적어라. 본문 글자와 배경의 대비는 WCAG AA(4.5:1) 이상을 지킨다.

### 글꼴

- 본문 기본 글꼴: Pretendard. OFL 라이선스라 앱에 포함할 수 있다. 공식 저장소에서 받아 번들하고 라이선스 파일도 함께 넣어라. (글꼴 파일은 외부 라이브러리 금지 규칙의 예외다.)
- 본문 선택지: Pretendard, Apple SD 산돌고딕 Neo, AppleMyungjo(명조). 설정에서 고른다.
- UI 글꼴(사이드바, 메뉴, 설정): 시스템 기본 글꼴. 본문 글꼴과 섞지 않는다.
- 숫자(글자 수 등)는 고정폭 숫자(tabular figures)로 표시해 값이 바뀔 때 흔들리지 않게 한다.

### 편집 영역 기본값

| 항목 | 기본값 | 설정 범위 |
|---|---|---|
| 글자 크기 | 17pt | 13~24pt |
| 줄 간격 | 1.75배 | 1.4~2.2배 |
| 문단 간격 | 0.6줄 | 0~1.5줄 |
| 본문 폭 | 한 줄 약 40자 | 30~55자 |
| 좌우 여백 | 창이 넓으면 본문을 가운데 두고 나머지는 여백 | |

- 본문 폭은 창 너비와 관계없이 고정한다. 넓은 창에서 줄이 끝없이 길어지면 안 된다.
- 위아래로도 넉넉한 여백을 둔다. 마지막 줄까지 화면 가운데 근처로 끌어올려 쓸 수 있어야 한다.

### 화면 구성

- **사이드바**: 작품 제목, 회차 목록(번호, 제목, 글자 수는 inkMuted로 작게). 선택한 회차만 은은하게 표시. 아이콘은 꼭 필요한 곳에만 SF Symbols로.
- **상태 표시**: 편집 영역 아래쪽에 한 줄. 글자 수, 목표 진행률, 저장 상태. 타이핑을 시작하면 서서히 흐려지고, 마우스를 움직이거나 타이핑을 멈추면 다시 나타난다.
- **저장 상태**: "저장됨" 같은 알림을 띄우지 않는다. 저장 중이거나 실패했을 때만 표시한다. 실패는 눈에 띄게.
- **빈 화면**: 작품이 없거나 회차가 없을 때 짧은 안내 한 줄과 버튼 하나. 일러스트나 이모지는 넣지 않는다.

### 움직임

- 애니메이션은 상태 변화를 알려줄 때만 쓰고, 150ms 이내로 짧게 한다.
- 타이핑 중에는 어떤 애니메이션도 입력을 늦추면 안 된다.
- 시스템의 "동작 줄이기" 설정을 따른다.

### 디자인 확인 방법

- 화면 작업이 있는 단계가 끝날 때마다 각 화면의 스냅샷 이미지를 라이트와 다크 두 가지로 만들어 `docs/design-snapshots/` 폴더에 저장하고 보고에 포함해라. 빈 화면, 회차가 많은 화면, 긴 본문 화면을 포함한다.
- 스냅샷을 만들 수 없으면 내가 직접 확인할 수 있게 어떤 화면을 어떻게 띄우는지 알려줘라.

## 6. 저장 형식

작품 하나가 폴더 하나다.

```
내작품.novel/
  project.json        작품 제목, 회차 순서, 회차별 제목과 목표 글자 수, 설정값
  episodes/
    <고유ID>.md        회차 본문 (순수 텍스트)
  notes/
    <고유ID>.md        설정 노트 (인물, 장소 등)
  snapshots/
    <회차ID>/<시각>.md  회차별 버전 스냅샷
```

- 파일 이름은 변하지 않는 고유 ID를 쓴다. 회차 순서나 제목을 바꿔도 파일 이름은 바뀌지 않는다.
- 모든 쓰기는 원자적으로 한다(임시 파일에 쓴 뒤 교체). 저장 도중 앱이 죽어도 원고가 깨지면 안 된다.
- 본문은 UTF-8 일반 텍스트다. 다른 에디터로 열어도 읽을 수 있어야 한다.
- 원고 유실은 이 앱에서 가장 심각한 버그다. 저장 관련 코드는 테스트를 가장 꼼꼼히 작성해라.

### 저장 안정성

- **저장 순서 보장**: 같은 파일에 대한 저장은 한 번에 하나씩 순서대로 처리한다. 회차마다 변경 번호를 두고, 더 낮은 번호의 저장이 더 높은 번호의 내용을 덮어쓰지 못하게 한다. 늦게 끝난 옛 저장이 최신 원고를 되돌리는 일이 없어야 한다. 이 경우를 재현하는 테스트를 작성해라.
- **형식 버전**: `project.json`에 `schemaVersion` 숫자를 넣는다. 형식을 바꿀 때는 옛 버전을 읽어 새 버전으로 옮기는 코드를 함께 넣고, 앱이 모르는 더 높은 버전의 파일은 고치지 말고 열기를 거부한다.
- **`project.json` 보호**: 저장할 때 직전 정상본을 `project.json.bak`으로 남긴다. `project.json`이 깨졌으면 백업으로 복구하고, 백업도 없으면 `episodes/` 폴더의 파일들로 회차 목록을 다시 만든다. 어떤 경우에도 본문 파일을 지우지 않는다.
- **저장 실패**: 실패하면 짧은 간격으로 몇 번 다시 시도하고, 그래도 안 되면 화면에 눈에 띄게 알린다. 실패한 동안에도 편집 내용은 메모리에 유지하고, 그 상태로 앱을 닫으려 하면 경고한다.
- **종료 시 저장**: 앱을 끌 때 진행 중인 저장이 끝난 것을 확인한 뒤 종료한다.
- **외부 변경**: 창이 다시 활성화될 때와 저장 직전에 파일이 앱 밖에서 바뀌었는지 확인한다. 앱 쪽에 저장 안 된 변경이 없으면 조용히 다시 불러온다. 양쪽 다 바뀌었으면 덮어쓰지 말고, 앱 쪽 내용을 스냅샷으로 남긴 뒤 나에게 어느 쪽을 쓸지 묻는다.

## 7. 기능 (1차 버전)

1. **작품과 회차 관리**: 사이드바에 회차 목록. 추가, 삭제(확인 후 휴지통으로), 이름 변경, 드래그로 순서 변경.
2. **본문 편집기**: 글꼴, 글자 크기, 줄 간격, 본문 폭을 설정에서 조절. 라이트 모드와 다크 모드 모두 지원.
3. **글자 수**: 공백 포함과 공백 제외를 실시간으로 표시. 회차별 목표 글자 수와 진행률 표시. 사이드바에 회차별 글자 수 표시.
4. **자동 저장**: 입력이 멈춘 뒤 짧은 시간 안에 저장. 앱 종료, 회차 전환, 창 비활성화 때도 저장.
5. **버전 스냅샷**: 수동으로 찍기, 그리고 내용이 바뀌었을 때 일정 간격으로 자동 찍기. 스냅샷 목록에서 내용을 보고 복원할 수 있다. 회차당 보관 개수에 상한을 둔다.
6. **작품 전체 검색과 바꾸기**: 모든 회차를 대상으로 검색하고, 결과를 누르면 해당 위치로 이동. 바꾸기는 실행 전에 대상 개수를 보여주고 확인받는다.
7. **집중 모드와 타자기 스크롤**: 집중 모드는 사이드바와 부가 요소를 숨긴다. 타자기 스크롤은 입력 중인 줄을 화면 세로 가운데 근처에 유지한다.
8. **설정 노트 분할 화면**: 본문 옆에 설정 노트를 나란히 띄워 보면서 쓸 수 있다.
9. **내보내기**: 선택한 회차 또는 전체를 txt와 md로 내보낸다.

모든 주요 동작에 키보드 단축키를 붙이고 메뉴 막대에서도 실행할 수 있게 해라.

### 세부 기준 (제안값)

아래는 출발점으로 정한 값이다. 계획을 보여줄 때 이 목록을 함께 보여주고 내 확인을 받아라. 여기에 없는데 구현하다 정해야 하는 것이 생기면 임의로 정하지 말고 `docs/PLAN.md`의 "미결정 사항"에 적어 나에게 물어라.

- **글자 수**: Swift의 `String.count`(화면에 보이는 글자 단위)로 센다. "공백 포함"은 줄바꿈만 빼고 모두 센다. "공백 제외"는 공백, 탭, 줄바꿈을 뺀다. 조합 중인 글자도 한 글자로 센다.
- **자동 스냅샷**: 내용이 바뀐 회차에 한해 10분마다, 그리고 회차를 떠날 때(전환, 앱 종료) 마지막 스냅샷과 다르면 찍는다. 회차당 최근 50개까지 보관하고, 넘으면 오래된 자동 스냅샷부터 지운다. 내가 직접 찍은 스냅샷은 자동으로 지우지 않는다.
- **검색**: 입력한 문구를 그대로 찾는다(여러 단어를 따로 찾지 않는다). 영문 대소문자는 구분하지 않는 것이 기본이고 옵션으로 켤 수 있다. 줄을 넘어가는 검색은 하지 않는다.
- **전체 바꾸기**: 실행 직전에 바뀌는 회차 전부를 스냅샷으로 남긴다. 실행 후 한 번의 실행 취소로 전부 되돌릴 수 있어야 하고, 그게 어렵다면 스냅샷 복원 방법을 안내한다.
- **회차 삭제**: 휴지통으로 옮기지 못하면 삭제를 중단하고 알린다. 영구 삭제로 대신하지 않는다.
- **내보내기**: 전체 내보내기는 회차 순서대로 한 파일에 합치고, 회차마다 "N화 제목" 줄과 빈 줄로 구분한다. 회차별로 파일을 나누는 옵션도 둔다.
- **실행 취소**: 회차를 전환하면 실행 취소 기록은 비운다. 전환할 때 찍는 스냅샷이 안전망이다.

### 만들지 않는 것

AI 기능, 기기 간 동기화, 서식(굵게, 기울임 등), 맞춤법 검사, iOS 버전. 다만 나중에 붙일 수 있도록 길을 막는 구조는 피해라.

## 8. 성능 목표

감으로 판단하지 말고 측정해라. 아래는 이 M2 8GB 기기에서 릴리스 빌드 기준이다.

| 항목 | 목표 |
|---|---|
| 앱 실행부터 입력 가능까지 | 0.5초 이내 |
| 키 입력 한 번의 처리 시간 | 16ms 이내 (프레임 하나를 넘기지 않는다) |
| 대기 상태 메모리 | 100MB 이하 |
| 500회차 작품 열기 | 0.3초 이내 |
| 회차 전환 | 50ms 이내 |
| 500회차 전체 검색 | 0.5초 이내 |

지켜야 할 설계 원칙은 다음과 같다.

- 작품을 열 때 모든 회차 본문을 읽지 않는다. `project.json`만 읽고, 본문은 선택한 회차만 읽는다.
- 파일 저장, 글자 수 계산, 검색, 스냅샷은 메인 스레드를 막지 않는다.
- 키 입력마다 전체 본문을 복사하거나 SwiftUI 상태로 본문 전체를 흘려보내지 않는다. `NSTextView`의 텍스트 저장소를 본문의 원본으로 삼고, SwiftUI에는 필요한 값(글자 수 등)만 전달한다.
- 글자 수는 입력마다 전체를 다시 세지 말고, 그게 실제로 느린지 먼저 측정한 뒤 필요하면 증분 계산으로 바꿔라.

측정 도구를 직접 만들어라.

- 500회차, 회차당 5,000자짜리 한국어 더미 작품을 만드는 생성기.
- 위 표의 각 항목을 재는 성능 테스트 (`XCTest`의 측정 기능이나 signpost 사용).
- 각 단계가 끝날 때 측정 결과를 표로 보고해라.

측정 기준은 다음과 같다.

- 모든 항목은 릴리스 빌드로 5회 이상 재고 중앙값을 기준으로 삼는다. 최솟값과 최댓값도 함께 적는다.
- **앱 실행**: 프로세스 시작부터 편집기가 첫 키 입력을 받을 수 있을 때까지. 한 번 실행한 적이 있는 상태를 기준으로 하고, 재부팅 직후 첫 실행 값은 참고로만 적는다.
- **키 입력**: 키 이벤트를 받은 때부터 글자가 반영되고 레이아웃이 끝날 때까지. 5,000자 회차에서 1,000번 입력해 95번째 백분위수(p95)가 16ms 이내여야 한다. 최댓값도 적는다.
- **대기 메모리**: 5,000자 회차 하나를 열고 30초 가만히 둔 뒤의 메모리 사용량. 편집 중 값은 참고로 따로 적는다.
- **500회차 작품 열기**: 열기를 요청한 때부터 사이드바와 선택된 회차 본문이 보일 때까지.
- **회차 전환**: 회차를 선택한 때부터 본문이 보일 때까지. 이번 실행에서 처음 여는 회차 기준.
- **전체 검색**: 검색을 실행한 때부터 모든 결과가 나올 때까지. 첫 검색과 두 번째 이후 검색을 따로 적는다.

목표에 못 미쳤을 때는 숨기지 말고 이렇게 처리한다. 원인을 조사해 보고하고, 고치는 데 드는 대략의 크기와 대안을 제시한 뒤 멈춘다. 계속 고칠지, 목표를 조정할지, 다음 단계로 넘어갈지는 내가 정한다. 수치 하나를 맞추려고 혼자 오래 매달리지 마라.

## 9. 한글 입력

한글 입력이 깨지면 이 앱은 쓸모가 없다.

- 한글은 조합 중인 글자가 있다(`hasMarkedText`). 조합 중에는 텍스트 저장소를 프로그램에서 수정하거나, 선택 영역을 바꾸거나, 뷰를 다시 만드는 일을 하지 않는다.
- 자동 저장, 글자 수 갱신, 타자기 스크롤, 스타일 적용이 조합을 끊지 않는지 각각 확인해라.
- SwiftUI 상태가 바뀔 때 `updateNSView`에서 텍스트를 다시 넣어 조합이 끊기는 문제가 흔하다. 이 경로를 특히 조심해라.
- 자동 테스트로 검증하기 어려운 부분이니, 내가 손으로 확인할 체크리스트를 만들어 달라 (예: 빠르게 연타, 조합 중 방향키, 조합 중 회차 전환, 조합 중 저장 시점).

## 10. 작업 방식

1. **계획 먼저**: 코드를 쓰기 전에 환경을 확인하고, 4장의 폴더 뼈대와 `README.md`, `CLAUDE.md`, `docs/SPEC.md`를 만든 뒤 `docs/PLAN.md`에 단계별 계획을 적어라. 각 단계는 "빌드되고 내가 직접 실행해서 확인할 수 있는 상태"로 끝나야 한다. 계획을 보여주고 내 승인을 받은 뒤 시작해라.
2. **디자인 문서**: 계획과 함께 `docs/DESIGN.md`를 작성해라. 5장의 값을 정리하고, 5장에 없는 결정(사이드바 폭, 아이콘, 설정 창 구성 등)을 채운다. 이것도 내 승인을 받는다.
3. **권장 순서**: 뼈대와 `NovelCore` 저장 계층, 편집기와 한글 입력 검증, 회차 관리와 자동 저장, 글자 수, 검색, 스냅샷, 집중 모드와 타자기 스크롤, 설정 노트 분할, 내보내기, 마무리 최적화. 저장과 자동 저장은 편집기 바로 다음에 만들어 일찍부터 검증하고, 5장의 색과 글꼴 토큰은 나중에 입히지 말고 첫 화면부터 적용한다. 더 나은 순서가 있으면 계획에서 제안해라.
4. **단계마다**: 빌드하고, 테스트를 돌리고, 성능을 재고, 쓰지 않는 파일을 정리하고, `docs/PROGRESS.md`를 갱신하고, git 커밋을 남긴다. 그런 다음 멈추고 나에게 보고해라. 내가 승인하면 GitHub에 푸시한다. 보고에는 무엇을 만들었는지, 내가 어떻게 실행하는지, 무엇을 손으로 확인해야 하는지, 성능 측정 결과, 화면이 바뀌었다면 디자인 스냅샷을 담는다.
5. **테스트**: `NovelCore`는 단위 테스트를 작성한다. 특히 저장, 원자적 쓰기, 순서 변경, 스냅샷 복원, 검색과 바꾸기.
6. **막히면**: 같은 문제로 여러 번 실패하면 계속 시도하지 말고, 시도한 것과 원인 추정을 정리해서 나에게 물어라.
7. **완료 기준을 속이지 마라**: 빌드가 안 되거나 테스트가 실패하거나 성능 목표에 못 미치면 그대로 말해라. 테스트를 지우거나 목표 수치를 낮춰서 통과시키지 마라.

### 사용량 한도를 고려한 작업

나는 구독 플랜으로 Claude Code를 쓴다. 5시간 단위 세션 한도와 주간 한도가 있고, 한도에 걸리면 작업이 중간에 끊긴다. 그래서 언제 끊겨도 폴더가 깨끗하고 다음 세션에서 바로 이어갈 수 있어야 한다.

**끊겨도 안전하게**

- 단계는 한 세션 안에 여유 있게 끝날 크기로 나눈다. `docs/PLAN.md`의 각 단계에 예상 크기(작음, 중간, 큼)를 적고, "큼"은 더 쪼개라.
- 동작하는 작은 단위마다 커밋한다. 빌드가 깨진 상태를 오래 끌지 않는다.
- 작업을 시작할 때와 중간중간 `docs/PROGRESS.md`의 "지금 하는 일"과 "다음 할 일"을 갱신한다. 새 세션이 이 문서만 읽고 이어갈 수 있을 만큼 구체적으로 쓴다(어떤 파일의 무엇을 하던 중인지).
- 한도가 가까워졌다는 경고가 보이면 새 작업을 시작하지 않는다. 하던 일을 마무리하고, 커밋하고, `docs/PROGRESS.md`를 갱신한 뒤 멈춘다.
- 내 허락 없이 추가 요금이 드는 방식(사용 크레딧, API 크레딧)으로 넘어가지 않는다. 한도에 걸리면 재설정을 기다린다.

**토큰을 아껴 쓰기**

- 세션을 시작하면 `CLAUDE.md`와 `docs/PROGRESS.md`를 먼저 읽고, 그 작업에 필요한 파일만 읽는다. 저장소 전체를 훑지 않는다.
- 큰 파일을 통째로 반복해서 읽지 않는다. 필요한 부분만 찾아 읽는다.
- 빌드와 테스트 출력은 길다. `Scripts/`의 스크립트는 성공하면 한 줄 요약만, 실패하면 오류 부분만 출력하게 만들어라. 전체 로그는 `build/logs/`에 저장한다.
- 같은 방법을 되풀이하지 않는다. 두 번 실패하면 접근을 바꾸거나 나에게 묻는다.
- 꼭 필요하지 않으면 하위 에이전트나 병렬 작업을 쓰지 않는다. 메모리 8GB에도 부담이다.
- 보고는 짧게 한다. 이미 문서에 있는 내용을 되풀이하지 말고 문서 위치를 알려줘라.
- 이 절의 핵심 규칙은 `CLAUDE.md`에도 요약해 넣어라.

## 11. 코드 규칙

- 들여쓰기는 스페이스 2칸.
- 나는 Swift 초보다. 보고할 때 새로 등장한 개념(예: actor, `NSViewRepresentable`)은 한두 문장으로 설명해라. 코드 주석은 "왜 이렇게 했는지"가 필요한 곳에만 한국어로 단다.
- 파일 하나가 한 가지 역할만 하도록 나눠라. 필요 없는 추상화와 미리 만들어 두는 기능은 넣지 않는다.
- 앱 이름은 임시로 `NovelEditor`로 한다. 나중에 바꾸기 쉽게 한곳에서 관리해라.
- 나와의 대화, `PLAN.md`, 보고는 모두 한국어로 한다.

지금 환경 확인, 폴더 뼈대 만들기, `docs/PLAN.md`와 `docs/DESIGN.md` 작성부터 시작해라.

## 변경 사항 (사용자 결정, 2026-11-10)

- 작품 여는 방식: Obsidian의 볼트 선택처럼, 앱을 열면 작품 선택 창이 먼저 뜨고, 작품을 고르면 그 작품 폴더의 작업 공간으로 들어간다. 작품마다 폴더가 따로 있다.
- 글자 수: 설정에서 표시 방식(공백 포함 / 공백 제외 / 둘 다)과 목표 진행률 기준(공백 포함 / 공백 제외)을 고를 수 있다. 기본은 둘 다 표시, 목표는 공백 포함.
- 그 밖의 결정은 `docs/PLAN.md` 6장 "결정된 사항"에 있다.
- 설정은 두 층: 글꼴 같은 앱 전체 설정과, 작품 폴더 안 `project.json`의 작품별 설정. 작품은 Finder에서 폴더로 관리하고 앱은 따로 추적 정보를 두지 않는다. 나중에 맞춤법 검사를 붙이면 고유명사·캐릭터 이름 예외 사전도 작품 폴더 안에 둔다.
- 새 작품은 만들 때마다 위치를 묻는다.
