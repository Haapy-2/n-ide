- **이유**: 실제 원고에서 여러 커서가 이상하면 작가가 바로 끄고, 여러 커서로 망친 글을 되찾을 수 있게(PLAN 16장 4번 안전망, 6번 ④).
- **근거**: 사용자 요청("다음 작업 시작해", 포테이토 모드). PLAN 16장 4번 안전망 목록.
- **결과**: 설정 › 편집기 `같은 말 여러 커서`(기본 켬). 끄면 메뉴 흐림, ⌘D 아무것도 안 함, 여러 커서 중이면 조합 확정 뒤 하나로. 커서가 둘이 되는 순간 새 종류 `여러 커서 전`(`multicursor`) 스냅샷(마지막과 같으면 건너뜀, 보관 개수로 정리, 종료 때 기다림). 한도에서 경고음 대신 토스트. `perf.sh`에 "키 입력 300번 (10만 자, 커서 100개)" 줄. 한글 체크리스트 23~28번. 테스트: NovelCore `multiCursorIsNamedListedAndPrunedWithAuto`, 앱 `testTurnedOffCommandDDoesNothing`·`testTurningOffDuringCompositionCommitsAndEnds`·`testEnterCallbackOnlyWhenSecondCursorAppearsBeforeAnyChange`·`testBridgeCarriesLimitNoticeAndSwitch`·`testEnteringMultiCursorSnapshotsTextBefore`. NovelCore 208개·앱 271개(건너뜀 16) 통과.
- **에러**: 새 성능 줄이 목표 미달. Release, 부하 평균 2.8~4.3, 10만 자에 1,000자마다 표시어 100곳: p95 39.3ms(목표 16ms). 다른 키 입력 줄과 같이 키마다 `ensureLayout(for: textContainer)`로 본문 전체 레이아웃까지 잰다.
- **원인 조사(임시 측정, 커밋 안 함)**: 같은 조건에서 고치기만 p95 3.4ms, 고치기 + 화면 그리기(`displayIfNeeded`, 보이는 곳까지 레이아웃) 3.7ms, + 본문 전체 레이아웃 40ms. 커서 하나 줄들은 끝 쪽만 바뀌어 전체 레이아웃이 싸지만, 여러 커서는 본문 전체에 흩어진 100곳이 바뀌어 전체 다시 레이아웃이 대부분이다. 실제 앱은 보이는 곳만 바로 레이아웃하고 나머지는 뒤에서 나눠 한다. 줄 번호를 켜면 화면 그리기까지 12.5ms(자리마다 줄 수를 다시 세는 것, 조사 A7).
- **수정**: 측정 정의를 사용자에게 물음 → "추천대로"(2026-11-26): 목표 줄은 화면 그리기까지, 본문 전체 레이아웃 값은 참고 줄로 함께 보인다(편집기 묶음 A 고침 뒤 반영).

## 버그 묶음 A: 여러 커서 맞닿은 지우기 ⌘Z, 외부 변경, 회차 전환 늦은 커서 옮기기, 줄 번호 다시 세기 + 커서 100개 측정 줄 둘로

- **근거**: 조사 결과 `build/audit/2026-11-26-findings.md` 묶음 A. 사용자 요청("버그 가능성을 조사하고 고쳐줘"). 측정 줄 정의는 사용자 결정("추천대로").
- **결과**:
  - A1: ⌘D로 고른 맞닿은 두 자리("가가")를 지우면 되돌리기 기록이 한 점에서 시작하는 범위 둘([0,0],[0,0])이 되어 `MultiCursor.edit`이 낡은 기록으로 보고 거절 → ⌘Z가 아무것도 안 하고 기록만 사라지고, 다음 ⌘Z가 그 아래 기록을 지금 본문에 적용해 엉뚱한 글자를 지웠다.   - A2: 여러 커서 중 외부 변경은 "앱 쪽 변경 있음"으로 묻는다(PLAN X4).
  - A3: 회차를 연 뒤 한 차례 늦게 커서 자리를 다시 맞출 때, 그사이 조합이 시작됐거나 커서가 움직였으면 옮기지 않는다.
  - A4: 외부 변경 불러오기·회차 전환에서 입력기에도 조합을 잊으라고 알린다(`forgetInputInProgress`).
