## 9단계: 글자 수와 상태 표시줄 (`08a0d02`)
- **이유**: 웹소설은 회차 분량(보통 5,000자 안팎)을 맞춰 연재하므로 쓰는 동안 글자 수와 목표 진행률이 보여야 한다.
- **근거**: SPEC 7장 3번·8장("먼저 재고 느리면 증분"), PLAN 4장 9단계·결정 사항 3·6, DESIGN 4장 상태 줄·사이드바, PERFORMANCE 2장(키 입력 경로).
- **결정**:
  - NovelCore `CharacterCount`: `Character` 단위, 공백 포함 = 줄바꿈만 뺌, 공백 제외 = 모든 빈칸 문자(전각 공백 포함) 뺌. 목표 기준 `CharacterCountBasis`.
  - 글자 수 저장 위치: `project.json`의 회차 정보(`characterCount`, 선택 값). 사이드바가 본문을 읽지 않고 보여주려면 필요. 본문에서 다시 셀 수 있는 값이라, 저장은 3초 미뤄 묶고(입력 멈춤마다 쓰지 않음) 창을 닫을 때 남은 것을 쓴다. 형식 버전은 올리지 않음(없는 키는 nil로 읽고, 옛 앱은 모르는 키를 무시).
  - 세는 때: 키 입력마다 세지 않고 입력이 0.3초 멈추면 본문을 한 번 복사해 메인 스레드 밖에서 전체를 센다(`CharacterCounter`). 텍스트 저장소 알림으로 입력·실행 취소·외부 변경 다시 읽기를 모두 잡는다. 키 입력 때는 시각만 적고, 기다리는 작업은 하나만 둔다.
  - 회차 전환: project.json에 있던 값을 바로 보여주고 새로 센 값으로 바꾼다. 떠나는 회차에 아직 안 센 입력이 있으면 편집기에 옛 본문이 남아 있을 때 먼저 센다.
  - 상태 줄(`StatusBar`): 편집 영역 아래 28pt, 본문 폭에 맞춤. 왼쪽 글자 수(설정의 표시 방식), 오른쪽 진행률 `24%` + 2pt accent 막대(100% 넘으면 숫자만 계속), 오른쪽 끝 저장 상태(저장 중…/저장 실패 · 다시 시도 중/저장 실패 · 원고는 메모리에 있음, 마지막은 누르면 이유). 편집기 위에 겹치지 않게 아래에 따로 둠.
  - 흐려짐(`StatusBarFade`): 타이핑 1초 뒤 150ms로 사라지고 입력 1.5초 멈춤·마우스 움직임에 나타남. SwiftUI 상태는 한 번 타이핑하는 동안 두 번만 바뀐다. 실패 표시는 흐려지지 않음. 동작 줄이기면 애니메이션 없음.
  - "다시 시도 중" 표시를 위해 `SaveQueue.save(..., onRetry:)` 추가, 자동 저장 상태에 `.retrying`.
  - 목표 글자 수: 회차 메뉴·사이드바 우클릭 "목표 글자 수…"(숫자만 받음, 0 이하 무시, ⌘Z로 되돌림). 이름 변경·순서 변경을 되돌려도 글자 수는 지금 값을 이어받음.
  - 설정 키: `characterCountDisplay`(`CharacterCountDisplay`: both/withSpaces/withoutSpaces, 기본 both), `characterCountGoalBasis`(기본 withSpaces). 설정 창은 10단계 몫이라 화면은 아직 없음(10단계 세션과 키 이름 약속함).
  - `make-dummy-novel`이 글자 수도 project.json에 넣는다.
- **측정(전체 계산 속도, 릴리스)**: 5,000자 0.3ms, 10만 자 6ms, 편집기에서 꺼낸 문자열(NSString) 10만 자 20ms → 증분 계산은 만들지 않음.
  - **수정**: 세기 전에 Swift 문자열로 바꾸면(`makeContiguousUTF8`) 편집기 문자열 10만 자 20ms → 10ms. NovelCore 안에서 한다.
- **에러 1**: 테스트 기대값을 손으로 잘못 셈(대사 문단 공백 제외 15→16, "방금 쓴 문장" 6→7). 코드는 맞았음.
- **에러 2**: 상대 경로로 준 더미 작품 경로를 `swift test`가 패키지 폴더 기준으로 읽어 못 찾음 → 절대 경로로.
- **결과**: NovelCore 테스트 57개, 앱 테스트 41개(건너뜀 3) 통과. 성능: 키 입력 p95 1.3ms(글자 수 세기·흐려짐 포함해 잼), 회차 전환 2.3ms, 500회차 열기 1.3ms(project.json에 글자 수가 들어가 0.7→1.3ms), 앱 실행 524.7ms(기존 미달, 17단계), 대기 메모리 86MB.
  - 메모리가 지난번 73MB보다 높아 같은 때 이전 커밋 릴리스 빌드와 번갈아 3번씩 잼: 이전 70·74·76MB, 이번 84·75·75MB → 차이 없음(흔들림).
- **남긴 것**: 앱을 끌 때는 미뤄 둔 글자 수 저장을 기다리지 않는다(종료 직전 3초 안에 바뀐 글자 수만 해당, 그 회차를 열면 다시 셈). 글자 수가 없는 옛 작품·복구로 다시 만든 목록의 회차는 열기 전까지 사이드바 글자 수가 비어 있다.

## 상태 줄 다듬기: 글자 수 실시간, 상태 줄 숨기기 설정, 위 여백 반 (`47cf8b2`)
- **이유**: 사용자 요청. 치는 동안 글자 수가 바로 바뀌고 상태 줄이 떠 있기를 원함. 쉬고 있을 때는 10초 뒤 사라지게(설정 가능), 글자 수 갱신 주기를 실시간·0.1·0.2·0.3초 슬라이더로. 첫 줄 위 빈 공간을 반으로.

- **결과**: ① `doc.text`로 바꿈. ② 시스템 선택을 쓰지 않고 작업 공간 사이드바와 같은 방식(줄을 누르면 선택, `rowHighlight`의 회색 칸 `rowSelected`·마우스 올림 `rowHovered`). 테마 세그먼트의 파란 칸은 시스템 버튼이라 그대로. 앱 테스트 통과.
- **에러**: 간격 15pt를 넣은 뒤 사용자가 "안 바뀐다"고 함. 빌드는 새것(코드에도 15)이었고, 다시 열어 보니 반영돼 있었다(예전 창이 떠 있었던 것으로 보임). 화면 제어 권한 요청은 이 환경에서 뜨지 않아 두 번 시도 후 그만두고 사용자 스크린샷으로 확인.

## 11단계 계획: 버전 스냅샷과 비교 (계획만, 코드 없음) (`1aea1ab`)
- **이유**: 사용자 요청. 11단계(스냅샷)에 비교(diff)를 합쳐서, 실수 없이 갈 수 있게 계획부터 세움.
- **근거**: SPEC 6장(`snapshots/` 형식)·7장, PLAN 5장 자동 스냅샷 기준, DESIGN 스냅샷 시트·단축키, 8단계 `ConflictSnapshot.swift`·`EpisodeAutosaver`(떠날 때 저장 본문 재사용) 코드. 사용자 답변: 상한 넘으면 오래된 것부터 휴지통 없이 바로 삭제, 스냅샷을 누르면 과거↔현재 비교(문장·어절·글자 단위로 칠하기, VS Code처럼 줄 번호), 메모 넣기, 누가 고쳤는지는 CLI·MCP 때로 보류, 편집기 줄 번호 설정(켜고 꺼도 본문 안 움직임), 비교는 떠 있는 판(바깥 클릭·Esc로 닫힘), 복원은 양쪽 방향 모두 스냅샷으로 기록.
- **결과**: PLAN 4장 11단계 줄·단계별 내용 고침, 10장 상세 계획 추가(11a~11g), 미결정 사항 11~15 추가. 참고 이미지 2장 `docs/design-snapshots/11-ref-diff.png`, `11-ref-floating-panel.png`(두 번째는 사용자 화면 캡처라 개인 정보가 보이는 사이드바·대화 부분을 잘라내고 판만 남김).
- **추가(사용자 요청)**: 설정 → 일반에 자동 스냅샷 켜기/끄기와 간격(5·10·15·30·60분, 기본 켬·10분). PLAN 10장 3번·8번, 미결정 16(끄면 떠날 때도 끌까, 추천: 떠날 때는 유지).

## 11단계 미결정 사항 11~16 결정 (계획만, 코드 없음)
- **이유**: 사용자 요청. 11단계를 시작하기 전에 남은 질문을 정리.
- **근거**: 사용자 답변. 11~14·16은 추천대로, 15는 설정에서 사용자가 고르게(10~100), 자동 기본 간격 30분, 떠날 때는 늘 찍기.
- **결과**: PLAN 6장에 11~16 결정 추가, 7장에서 뺌. 10장: 회차 전체 복원 + 과거 칸 복사(덩어리 되돌리기는 나중), 과거↔현재만, 줄 번호 문단마다·기본 꺼짐, 설정 → 일반 → 스냅샷에 `보관 개수`(10~100, 10 단위, 기본 50, auto·leave만), 자동 기본 30분(10분에서 바꿈), 테스트·용량 줄 고침. 4장·5장 요약도 맞춤. SPEC 7장의 "10분·50개"는 요구사항 원문이라 그대로 두고 PLAN을 따른다.

## 설정 창 목록 아이콘을 닫기 버튼 선에 맞춤 (`d47ff99`)
- **이유**: 사용자 요청. 아이콘을 빨간 닫기 버튼 기준으로 정렬, 아이콘~이름 15pt 간격 없애기, 이름은 패널 가운데(A안 선택), 기존 측정기와 연결하되 병목 없이.
- **근거**: 실행 중 측정(릴리스): 닫기 버튼은 창 왼쪽 9pt, 시스템 List는 줄을 16pt부터만 그림(표 칸 안쪽 여백) → 아이콘이 버튼 선보다 17pt 오른쪽(회색 칸 여백 10 포함). 사용자가 1번(List 빼고 줄 직접 쌓기) 선택. 처음 열 때 아이콘이 옮겨지는 게 보일 수 있다는 점에 사용자가 "재기 전 숨기기" 채택.
- **결과**: `SettingsView` 왼쪽 목록을 `VStack` 줄 3개로 바꾸고, 패널 왼쪽 끝에 `TrafficLightOffsetReader` 하나만 붙여 잼. 거리를 반씩 나눠 회색 칸 바깥 여백·칸 안 아이콘 여백(`RowLayout`), 재기 전 아이콘 숨김. "잰 값 → 여백" 계산(4~40, 전체 화면 8)을 `TrafficLightOffsetReader.contentInset(for:)`로 옮겨 작업 공간 사이드바와 같이 씀. 창마다 버튼 거리가 달라 값을 창끼리 나누지 않음. 설정 창은 크기 고정이라 사실상 열 때 한 번만 잼. NovelCore 57개·앱 68개 통과. 스냅샷: 예전에는 List가 스냅샷에 안 찍혔는데 이제 목록이 찍힘.
- **측정(릴리스, 임시 시험 코드로 재고 지움)**: 처음 열기(메뉴 → 창 그림) 고치기 전 179~202ms(앱 첫 실행 322ms), 고친 뒤(List 없음) 177~184ms(첫 실행 365ms). 아이콘은 첫 그림 뒤 약 10~17ms에 나타남. 잰 값 9pt.
- **에러**: `showSettingsWindow:` 동작 보내기로는 설정 창이 안 열려 시험 코드가 멈춤(앱 메뉴 항목 ","를 눌러 열게 바꿈). 처음엔 List를 둔 채 여백만 바꿨더니 잰 값이 -17(줄 여백 0으로 해도 -7)이라 4로 묶여 버튼 선에 못 감. 화면 제어 권한 요청은 사용자가 중단.
- **수정**: List를 빼고 줄을 직접 쌓아 잰 값 9 → 아이콘 왼쪽 끝 = 버튼 왼쪽 끝(창 그림으로 확인).

## 설정 창 목록 이름 가운데 정렬 되돌림 (`3b02eb5`)
- **이유**: 사용자가 실제 화면을 보고 "글자는 가운데 정렬 안 하는 게 낫겠다, 글자만 되돌려, 아이콘은 그대로".
- **결과**: 이름을 아이콘 오른쪽에 왼쪽 정렬(아이콘 칸 폭 20, 왼쪽 붙임으로 아이콘은 버튼 선 유지). 아이콘~이름 간격은 시스템 기본(15pt는 계속 없음). 스냅샷 다시 찍음.

## 되돌리기 테스트의 선택자를 컴파일러 확인 방식으로 (`ef1e8d9`)
- **이유**: 사용자가 직접 고친 것. `Selector(("undo:"))`(문자열) → `#selector(ManuscriptTextView.undo(_:))`. 이름이 틀리거나 메서드가 없어지면 실행 전에 컴파일러가 잡는다.
- **결과**: 가리키는 선택자는 같은 `undo:`(`ManuscriptTextView`에 `@objc func undo(_:)`). 들여쓰기만 2칸 규칙에 맞춤. 앱 테스트 68개 통과(이 수정을 넣은 상태로 돌림).
