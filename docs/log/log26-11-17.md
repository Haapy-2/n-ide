## 병목·안정화 점검 (`aeb6294`)
- **이유**: 사용자 요청 "병목, 최적화할 부분, 안정화할 부분을 찾아서 고쳐". 스냅샷·자동 저장·비교·회차 목록·저장 줄 코드를 읽고, 의심 가는 곳은 조각별로 재서 확인한 것만 고쳤다.
- **찾아서 고친 것**:
  1. **스냅샷 목록 읽기가 느렸다**(병목). 조각별 측정: 50개 목록 읽기 12.6ms, 마지막 스냅샷 읽기 0.04ms, 쓰기 0.7ms. 목록을 찍을 때 한 번·정리할 때 한 번 읽어서 "스냅샷 찍기 26ms"의 거의 전부였다. 원인은 파일마다 `DateFormatter`를 새로 만들고 그것으로 시각을 해석한 것. 11a 기록의 "fsync가 대부분으로 보인다"는 추정은 **틀렸다**.
     - **시도 1**: 목록 하나에 해석기 하나만 → 5.4ms(해석 자체도 느림).
     - **수정**: 숫자를 직접 잘라 `Calendar`로 시각을 만들고, 이름을 만들 때도 같은 달력을 씀 → 목록 0.84ms, **스냅샷 찍기 26ms → 2.1ms**(10만 자 2.5ms). 없는 시각(13월, 25시)은 모르는 파일로 본다. 파일 이름 모양은 그대로.
  2. **스냅샷을 못 썼을 때 그 변경이 다시 찍히지 않았다**(안정화). 찍기 전에 "고친 회차" 표시를 지워서, 디스크가 꽉 찼을 때처럼 쓰기가 실패하면 다음 간격에도 안 찍혔다 → 실패하면 표시를 되돌려 다음 간격·떠날 때 다시 찍는다(직접 찍기는 화면에 오류를 알리므로 제외).
  3. **끝난 스냅샷 쓰기를 "남은 일"로 세고 있었다**(안정화). 쓰기 줄의 마지막 작업을 계속 들고 있어, 종료 때 할 일이 없는데도 기다리는 길로 갔다(결과는 같고 한 박자 늦음) → 안 끝난 쓰기 수를 센다.

- **이유**: 사용자 요청 "코드 전체적으로 점검, 버그가 날 수 있는 곳과 더 최적화할 곳을 찾아서 고쳐". 앞 점검에서 안 본 편집기·작품 열기·복구·작업 공간·설정까지 앱과 NovelCore 소스 전부(약 4,700줄)를 읽었다.
- **병목 1건**:
  - **타이핑 중 글자 수가 바뀔 때마다 작업 공간 전체를 다시 계산했다.** 글자 수를 `project.episodes[…].characterCount`에 적었는데, `project`는 작업 공간 화면 전체가 보는 값이라 숫자 하나가 바뀌면 사이드바 500줄까지 다시 계산됐다. 새 측정(`testSidebarCountUpdate`: 작업 공간을 실제로 띄우고 글자 수를 바꾼 뒤 화면 갱신까지) 중앙값 **17.5ms**, 최대 60ms. 치는 동안 0.2초마다 한 번이라 한 프레임(16ms)을 넘는 끊김이 될 수 있었다. 기존 키 입력 측정은 편집기만 띄워서 이것이 안 잡혔다.
    - **시도 1(효과 없음)**: 사이드바 줄을 `Equatable` 뷰로 묶기 → 16.8ms. 줄 내용이 아니라 목록 전체를 다시 훑는 값이 컸다.
    - **수정**: 글자 수를 회차마다 따로 둔 칸(`EpisodeCountBox`, `@Observable`)에 두고 사이드바의 그 줄만 읽게 함. `project`는 건드리지 않고 `project.json`에 쓸 때 합친다. → 중앙값 **0.7ms**, p95 0.9ms. perf.sh 표에 줄 추가(목표 16ms).
- **버그 가능성 4건**:
  1. **같은 작품이 창 두 개로 열릴 수 있었다.** 창의 값이 URL인데 끝의 `/` 하나만 달라도 다른 값이다(최근 목록은 `/`가 붙고 열기 창은 안 붙음). 작품을 연 채 "작품 전환…"으로 같은 작품을 다시 열면 창이 둘이 되고, 두 창이 같은 파일을 따로 저장한다(외부 변경 충돌 창이 뜨게 됨) → `ProjectLauncher.windowValue(for:)`로 한 모양으로 맞춘다.
  2. **종료 직전의 `project.json` 저장을 기다리지 않았다.** 종료 때는 본문 저장만 확인해서, 회차 이름·순서·목표를 바꾸자마자(저장이 끝나기 전) 끄면 그 변경이 안 남을 수 있었다. 미뤄 둔 글자 수 저장(3초)도 버려졌다(알려진 문제에 있던 것) → 시작한 저장 수를 세고, 종료·창 닫기 때 글자 수까지 쓰고 끝나길 기다린다.
  3. **조합 중에 바꾼 글꼴·크기 설정이 본문에 안 입혀질 수 있었다.** 조합 중에는 텍스트 저장소를 안 건드리려고 건너뛰는데, 주석("다음 변경 때 다시 적용")과 달리 다시 입히는 코드가 없었다 → 표시해 두었다가 조합이 끝난 직후 입힌다.
  4. **깨진 `project.json`을 치우는 이름이 겹치면 열기가 실패했다.** 이름이 초 단위라 같은 초에 두 번 복구하면 옮기기가 실패 → 겹치면 `-2`, `-3`.
- **보고 고치지 않은 것**: 회차 전환 때 본문을 메인 스레드에서 바로 읽는 것(끊김을 없애려는 기존 결정, 2.3ms), 최근 작품 목록의 경로 확인(20개), 휴지통·되돌리기 순서. 문제를 못 찾았다.
- **결과**: 테스트 6개 추가(`StabilityTests` 5개: 창 값, 종료 전 project.json 저장, 종료 전 글자 수, 글자 수가 project를 안 건드림, 조합 뒤 모양 입히기 / NovelCore 1개: 연달아 복구). NovelCore 88개, 앱 86개(건너뜀 6) 통과.
- **측정**(perf.sh): 글자 수 바뀜 → 화면 갱신 p95 0.9ms, 스냅샷 2.1ms, 나머지 통과, 대기 메모리 75MB.
  - **앱 실행 545.1ms 미달**(앞 점검 때도 530·550ms). 코드 탓인지 보려고 11b 커밋(`c9a49c8`, 그때 499ms)을 따로 빌드해 번갈아 8번씩 잼: 이전 중앙값 528ms, 지금 540ms. 글자 수 칸을 뺀 빌드로도 이전 530ms, 지금 536ms. 한 번 한 번이 515~690ms로 흔들려 6~12ms 차이는 구분되지 않는다 → **같은 코드도 지금은 530ms 안팎**이라 기기 상태가 바뀐 것이고, 이번 변경으로 느려졌다는 증거는 없다. 목표 미달 자체는 그대로다(17단계에서 구간별로 재기로 한 항목).
  - "설정 바꿔 모양 다시 입히기"가 0.7 → 2.0ms(5,000자), 1.8 → 2.9ms(10만 자)로 나왔다. 목표(16ms) 안이고, 바로 앞에 새 측정(작업 공간 창 띄우기)이 들어간 순서 탓으로 짐작하지만 원인은 확인하지 않았다.
