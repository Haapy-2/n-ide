## 11a: 스냅샷 저장·메모·정리 (`5f18116`)

  - 이름 `<yyyyMMdd-HHmmss>-<종류>.md`, 같은 초·같은 종류면 `-2`, `-3`. 모양이 다른 파일(모르는 종류, `-1`, 숨김 임시 파일, 숫자 아닌 시각)은 목록에도 정리에도 안 잡힌다.
  - `skipIfSameAsLatest`: 가장 최근 스냅샷(종류 무관)과 같으면 찍지 않고 nil. 자동·떠날 때가 쓴다(11b). 직접 찍기는 같아도 찍는다.
  - 메모: 같은 이름 `.memo`. 앞뒤 공백을 다듬고, 비우면 메모 파일만 없앤다. 본문을 먼저 써서 메모 쓰기가 실패해도 본문 스냅샷은 남는다.

  - 8단계 `ConflictSnapshot.swift`(`writeConflictSnapshot`)를 없애고 앱의 두 곳이 `writeSnapshot(kind: .conflict / .external)`을 부르게 바꿈. 파일 이름은 전과 같다.
  - 측정: `SnapshotPerformanceTests`(50개 찬 회차에 비교 → 쓰기 → 정리), perf.sh 표에 두 줄. SPEC에 목표가 없어 회차 전환 목표 50ms를 기준으로 둠.
- **결과**: NovelCore 테스트 69개 통과(스냅샷 12개 추가). 측정(릴리스): 5,000자 중앙값 25.9ms, 10만 자 26.1ms. 크기와 거의 무관해 디스크에 내려 쓰는 시간(fsync)이 대부분으로 보인다(추정, 구간별로 재지는 않음). 메인 스레드 밖에서 부를 것이라 입력에는 영향 없음.
- **에러 1**: 앱 테스트가 두 번 모두 "The test runner hung before establishing connection"으로 실패. 그때 화면이 잠겨 있었다(`CGSSessionScreenIsLocked=Yes`, 새벽 1시 반). 앱·테스트 컴파일은 성공했고 실행 단계에서 멈춤 → 코드 문제가 아니라 잠긴 화면에서 앱을 띄울 수 없어서로 본다. 세 번째로 돌리지 않고, 화면이 풀린 때 다시 돌린다.

  - **수정**: 화면이 풀린 뒤(02:02) `Scripts/test.sh` 다시 → 앱 테스트 77개 통과(건너뜀 5). 11a 변경도 함께 확인됨.

## 11b: 스냅샷 찍는 시점 (`c9a49c8`)
- **이유**: 11a의 저장 코드를 실제로 부르는 때를 붙인다. ⌘Z가 사라지는 회차 전환 뒤의 안전망이자, 오래 쓰는 동안의 되돌아갈 지점.
- **근거**: 사용자 "다음 11단계 해줘", PLAN 10장 3번, 결정 사항 15·16, DESIGN 단축키 표(파일 → 스냅샷 찍기 ⌥⌘S).
- **결정**:
  - `App/Editor/EpisodeSnapshotter.swift`: 자동 저장기가 갖고 본문을 건네받는다. "마지막 스냅샷 뒤에 고친 회차" 목록만 들고 있다(키 입력 때는 이 목록에 넣기만, 본문 복사 없음).
  - 자동: 설정 간격마다 지금 회차를 그사이 고쳤을 때만 본문을 한 번 복사해 찍는다. 설정이 바뀌면 타이머를 다시 건다. 끄면 타이머만 멈춘다.
  - 떠날 때: 회차 전환(`leaveEpisode`), 창 닫기·앱 종료(`finish`: 떠날 때 스냅샷 → 저장 끝 → 스냅샷 쓰기 끝까지 기다림). 자동을 꺼도 찍는다. **이번에 고치지 않은 회차는 찍지 않는다**(내 판단: 훑어보기만 한 회차 500개에 스냅샷이 생기지 않게. PLAN의 "마지막 스냅샷과 다르면"보다 좁다). 저장하려고 복사한 본문이 있으면 그것을 그대로 쓴다.
  - 직접(⌥⌘S, 파일 메뉴): 저장을 먼저 끝내고 찍는다. 같아도 찍는다. 찍은 뒤 "스냅샷을 찍었어요" 창에 메모 칸(비워 두고 엔터 가능, `메모 없이`). 직접 찍은 뒤 더 고치지 않았으면 떠날 때 찍지 않는다.
  - 쓰기는 한 줄로 차례대로(앞 것이 끝나야 "마지막과 같은지"가 맞음), 메인 스레드 밖. auto·leave 뒤에 보관 개수로 정리(정리 실패는 다음에 다시).
  - 앱 종료: 저장 안 된 변경이 없어도 아직 안 찍은 떠날 때 스냅샷이 있으면 기다린다(`hasWorkBeforeQuit`).
  - 설정 → 일반 → "스냅샷": 자동 스냅샷(기본 켬), 간격 5·10·15·30·60분(기본 30), 보관 개수 10~100개(기본 50). 키 `autoSnapshotEnabled`·`autoSnapshotMinutes`·`snapshotRetention`. 고를 수 없는 값은 기본값이나 범위 안으로 맞춘다.
- **결과**: 앱 테스트 8개 추가(`SnapshotTimingTests`: 기본값·범위 맞춤, 고친 뒤 떠나면 찍음, 안 고치면 안 찍음, 자동 꺼도 떠날 때 찍음, 자동은 고쳤을 때만, 끄면 안 찍음, 간격 바꾸면 새 간격, 보관 개수로 자동만 정리, 직접은 저장 먼저·같아도 찍음). 전체 앱 테스트 77개(건너뜀 5), NovelCore 69개 통과.
- **측정**(perf.sh 전체, 릴리스): 모두 통과. 키 입력 p95 1.1ms, 실시간 10만 자 0.5ms, 회차 전환 2.3ms, 스냅샷 찍기 26.3ms/26.6ms, 앱 실행 499.3ms(경계), 대기 메모리 75.0MB.

## 11c: 비교 엔진 (`7be310f`)
- **이유**: 11d 비교 화면(과거↔현재 두 칸)이 그릴 결과를 만든다. 화면과 따로 둬서 나중에 "고친 기록"도 같은 모양으로 넘길 수 있게.
- **근거**: 사용자 "ㄱㄱ"(11c 시작), PLAN 10장 4번, 결정 사항 12·13(과거↔현재만, 문단마다 줄).
- **결정**:
  - NovelCore `TextDiff.swift`: `rows`(같은 줄·지운 줄·넣은 줄·고친 줄, 줄 위치는 0부터라 줄 번호 = +1), `oldLines`·`newLines`, `isLineOnly`, `hasChanges`.
  - 두 글을 NFC로 맞춘 뒤 줄바꿈으로 문단을 나눈다. 빈 글은 줄 0개(빈 글에서 쓰면 모두 넣은 줄).
  - 줄 비교: 앞뒤 같은 줄 잘라내기 → 줄마다 번호 붙이기 → 한쪽에만 있는 줄은 미리 빼고 양쪽에 다 있는 줄끼리만 `difference(from:)` → 붙어 있는 지운 줄·넣은 줄을 순서대로 짝지어 고친 줄로(남는 것은 지운 줄·넣은 줄).
  - 고친 줄 안: 어절(빈칸이 아닌 묶음)과 빈칸 묶음으로 나눠 비교. 지운 어절 하나와 넣은 어절 하나가 맞붙고 앞이나 뒤 글자가 같으면 다른 글자만(을→를, 했다→했었다는 현재 칸 "었"만), 아니면 어절 전체, 바뀐 글자가 줄 길이의 `wholeLineRatio`(기본 0.5)를 넘으면 줄 전체. 사이 빈칸은 칠하지 않음. 범위는 그 줄의 `Character` 위치라 한글 음절·합쳐진 이모지가 쪼개지지 않는다.
  - 고친 줄이 2,000개를 넘으면 줄 안 비교를 하지 않고 `isLineOnly`(화면에 알림). 도중에 취소되면 `CancellationError`.
  - "절반" 기준은 매개변수로 두고 11d에서 실제 원고로 보며 사용자와 정한다.
- **측정**(릴리스, 더미 5,000자 회차와 그것을 이어 붙인 10만 자, 10문단마다 하나 고치기·지우기·넣기):
  - 처음: 5,000자 0.5ms, 10만 자 25ms, 겹치는 문단이 하나도 없는 10만 자(2,861줄) **316ms**.
  - **수정 1**: 줄을 번호로 바꿔 비교(문자열 비교를 줄이려고) → 최악 155ms, 10만 자 20ms.
  - **수정 2**: 한쪽에만 있는 줄을 미리 빼고 비교 → 최악 **13.2ms**, 10만 자 16.8ms, 5,000자 0.7ms(번호 붙이기 몫이 조금 늘었음).
  - 줄 안 비교는 한 줄 약 0.013ms(2,861줄 전부 37ms) → 한도 2,000줄이면 26ms 안팎이라 그대로 둠.
  - SPEC에 목표가 없어 "스냅샷을 누르면 바로"로 100ms를 기준으로 둠. 모두 통과.
- **결과**: NovelCore 테스트 17개 추가(같은 글, 빈 글, 넣기·지우기, 짝짓기, 빈 줄, NFC/NFD, 글자·어절·줄 전체 판정, 기준 바꾸기, 이모지, 한도, 취소, 줄 빠짐없음) → 86개 통과. 앱 테스트 77개 통과(건너뜀 5, 앱 코드는 안 바뀜).

## 병목·안정화 점검 (커밋 해시는 다음 기록에)
- **이유**: 사용자 요청 "병목, 최적화할 부분, 안정화할 부분을 찾아서 고쳐". 스냅샷·자동 저장·비교·회차 목록·저장 줄 코드를 읽고, 의심 가는 곳은 조각별로 재서 확인한 것만 고쳤다.
- **찾아서 고친 것**:
  1. **스냅샷 목록 읽기가 느렸다**(병목). 조각별 측정: 50개 목록 읽기 12.6ms, 마지막 스냅샷 읽기 0.04ms, 쓰기 0.7ms. 목록을 찍을 때 한 번·정리할 때 한 번 읽어서 "스냅샷 찍기 26ms"의 거의 전부였다. 원인은 파일마다 `DateFormatter`를 새로 만들고 그것으로 시각을 해석한 것. 11a 기록의 "fsync가 대부분으로 보인다"는 추정은 **틀렸다**.
     - **시도 1**: 목록 하나에 해석기 하나만 → 5.4ms(해석 자체도 느림).
     - **수정**: 숫자를 직접 잘라 `Calendar`로 시각을 만들고, 이름을 만들 때도 같은 달력을 씀 → 목록 0.84ms, **스냅샷 찍기 26ms → 2.1ms**(10만 자 2.5ms). 없는 시각(13월, 25시)은 모르는 파일로 본다. 파일 이름 모양은 그대로.
  2. **스냅샷을 못 썼을 때 그 변경이 다시 찍히지 않았다**(안정화). 찍기 전에 "고친 회차" 표시를 지워서, 디스크가 꽉 찼을 때처럼 쓰기가 실패하면 다음 간격에도 안 찍혔다 → 실패하면 표시를 되돌려 다음 간격·떠날 때 다시 찍는다(직접 찍기는 화면에 오류를 알리므로 제외).
  3. **끝난 스냅샷 쓰기를 "남은 일"로 세고 있었다**(안정화). 쓰기 줄의 마지막 작업을 계속 들고 있어, 종료 때 할 일이 없는데도 기다리는 길로 갔다(결과는 같고 한 박자 늦음) → 안 끝난 쓰기 수를 센다.
  4. **지나간 회차의 본문이 메모리에 남았다**(최적화). 외부 변경 기준(`DiskVersions`)이 회차 본문 전체를 들고 있고 떠나도 지우지 않아, 훑어본 회차 수만큼 쌓였다(5,000자 500회차면 수 MB, 긴 회차면 더) → 떠난 회차는 저장할 것·쓰는 중인 것·충돌이 없을 때 기준을 놓는다. 다시 열면 디스크에서 새로 읽어 기준을 잡는다. 저장에 실패해 메모리에 남은 회차는 놓지 않는다.
- **보고 고치지 않은 것**(측정상 문제없음):
  - `project.json` 저장(500회차): 3.3ms, 메인 스레드 밖. 글자 수 때문에 타이핑 중 3초마다 한 번.
  - 회차 본문 쓰기 0.3ms, 회차 목록 다시 그리기(키 입력 p95 1.1ms 안에 포함).
  - 비교 엔진은 11c에서 이미 최악 316ms → 13ms로 고침.
- **결과**: 테스트 4개 추가(실패한 자동 스냅샷 다시 찍기, 떠난 회차 기준 놓기, 저장 실패 회차는 기준 유지, 이름 자릿수) + 없는 시각 이름 무시. NovelCore 87개, 앱 80개(건너뜀 5) 통과.
- **측정**(perf.sh 두 번): 스냅샷 찍기 2.1ms/2.5ms, 나머지 줄은 그대로 통과, 대기 메모리 74~76MB. **앱 실행은 530.5ms, 549.6ms로 미달**(목표 500ms). 같은 날 11b 뒤에는 499.3ms였다. 잴 때 부하 평균이 5 안팎이었고(499ms 때는 2.6, 연달아 빌드·테스트를 돌린 직후), 이번에 고친 코드는 실행 경로에 없다(스냅샷 목록·쓰기는 실행 때 안 불림). 기기 상태 탓으로 보지만 확인은 못 했다(두 번 재고 멈춤). 원래 경계값이라 17단계에서 구간별로 재기로 한 항목.
