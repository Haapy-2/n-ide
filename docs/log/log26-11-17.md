## 병목·안정화 점검 (`aeb6294`)
- **이유**: 사용자 요청 "병목, 최적화할 부분, 안정화할 부분을 찾아서 고쳐". 스냅샷·자동 저장·비교·회차 목록·저장 줄 코드를 읽고, 의심 가는 곳은 조각별로 재서 확인한 것만 고쳤다.
- **찾아서 고친 것**:
  1. **스냅샷 목록 읽기가 느렸다**(병목). 조각별 측정: 50개 목록 읽기 12.6ms, 마지막 스냅샷 읽기 0.04ms, 쓰기 0.7ms. 목록을 찍을 때 한 번·정리할 때 한 번 읽어서 "스냅샷 찍기 26ms"의 거의 전부였다. 원인은 파일마다 `DateFormatter`를 새로 만들고 그것으로 시각을 해석한 것. 11a 기록의 "fsync가 대부분으로 보인다"는 추정은 **틀렸다**.
     - **시도 1**: 목록 하나에 해석기 하나만 → 5.4ms(해석 자체도 느림).
     - **수정**: 숫자를 직접 잘라 `Calendar`로 시각을 만들고, 이름을 만들 때도 같은 달력을 씀 → 목록 0.84ms, **스냅샷 찍기 26ms → 2.1ms**(10만 자 2.5ms). 없는 시각(13월, 25시)은 모르는 파일로 본다. 파일 이름 모양은 그대로.
  2. **스냅샷을 못 썼을 때 그 변경이 다시 찍히지 않았다**(안정화). 찍기 전에 "고친 회차" 표시를 지워서, 디스크가 꽉 찼을 때처럼 쓰기가 실패하면 다음 간격에도 안 찍혔다 → 실패하면 표시를 되돌려 다음 간격·떠날 때 다시 찍는다(직접 찍기는 화면에 오류를 알리므로 제외).
  3. **끝난 스냅샷 쓰기를 "남은 일"로 세고 있었다**(안정화). 쓰기 줄의 마지막 작업을 계속 들고 있어, 종료 때 할 일이 없는데도 기다리는 길로 갔다(결과는 같고 한 박자 늦음) → 안 끝난 쓰기 수를 센다.

## 버그가 날 수 있는 곳 더 고치기 (`9282a24`)
- **이유**: 사용자 요청 "버그가 날 수 있는 곳을 해결해". 앞 점검에서 찾은 4건은 이미 고쳤으므로, 원고 유실·앱 멈춤과 이어질 수 있는 남은 곳을 더 찾았다.

## 세 번째 점검: 버그·메모리·병목 (`a74bed4`)
- **이유**: 사용자 요청 "코드를 전체적으로 분석해서 버그 발생 가능성, 메모리 조사, 최적화해야 할 코드와 병목 구간 조사해서 완화 작업 시작해줘". 앞의 두 점검에서 고친 것은 다시 보지 않고, 멈춰 있던 메모리 조사를 끝냈다.
- **근거**: 원고 유실이 가장 심각한 버그(CLAUDE.md), PERFORMANCE.md 3·6장, 앞 세션의 메모리 관찰(500회차 오가면 33 → 74MB, 10만 자 회차 +27MB, 창 복원에 따라 77 ↔ 89MB).
- **고친 것**:
  1. **휴지통에서 ⌘Z로 되살린 회차를 고치면 저장되지 않았다(원고 유실).** 휴지통으로 보낼 때 그 회차의 변경 번호를 0으로 되돌렸는데, 저장 줄(`SaveQueue`)은 그 회차에 쓴 마지막 번호를 기억하고 있어서, 되살린 뒤의 저장이 "옛 저장"으로 보여 건너뛰어졌다. 화면에는 저장된 것으로 보였다(앞서 고친 횟수만큼의 입력이 사라짐). 재현 테스트를 먼저 넣어 실패("하나 둘 셋" ≠ "하나 둘 셋 넷")를 확인 → 번호를 되돌리지 않고 "저장됨"으로만 표시 → 통과.
  2. **디스크에 내려 쓰기를 F_FULLFSYNC로.** 애플 기기의 `fsync`는 저장 장치 캐시까지 비우지 않아 갑자기 전원이 꺼지면 마지막 저장이 빠질 수 있다(애플 문서). 이 기기에서 잼: fsync 0.2ms → F_FULLFSYNC 2.9ms. 모든 쓰기가 메인 스레드 밖이라 입력과 무관. 지원하지 않는 디스크에서는 fsync로 대신한다. 스냅샷 찍기 3.1 → 6.6ms(목표 50ms).
  3. **하드 링크를 못 만드는 디스크에서 스냅샷이 늘 실패할 수 있었다.** 앞 점검에서 덮지 않기를 `link`로 했는데, exFAT·FAT 외장 디스크와 일부 네트워크 드라이브는 하드 링크가 없다. → `link`가 이름 겹침 말고 다른 이유로 실패하면, 빈 파일로 이름을 먼저 차지(O_EXCL)하고 다 쓴 임시 파일을 그 위로 바꿔 넣는다. 테스트 추가.
- **메모리 조사**(결과와 계획은 [PLAN.md 11장](../PLAN.md)):
  - 측정 `MemoryGrowthTests`: 사이드바 + 편집 영역을 띄우고 500회차 3바퀴 + 10만 자 회차 3번 열고 닫기, footprint와 malloc 사용량을 함께 찍는다. perf.sh 표 아래 한 줄로 나온다.
  - 쌓이는지는 malloc으로 본다: footprint는 같은 조건에서 78 → 111 → 89MB처럼 오르내린다(해제한 메모리를 malloc이 바로 돌려주지 않음).
  - 나눠 재기: 편집기만 → 0, 편집 영역(자동 저장기·글자 수 포함)만 → 0, 사이드바만 → 바퀴당 0.55MB, 둘 다 → 1.1~1.4MB(회차 전환 한 번에 2~3KB). 시스템 `List`만 → 0.
  - 줄 꾸밈을 하나씩 붙여 보기(회색 칸, 마우스 올림, 접근성, 우클릭 메뉴, 두 번 클릭, 줄 여백): 각각은 바퀴당 0.05~0.14MB로 원인 아님.

  1. 디자인 스냅샷을 찍다 앱이 죽음(`Range requires lowerBound <= upperBound`). 바뀐 줄 사이의 같은 줄이 6개 이하면 "앞 3줄 + 뒤 3줄"이 겹쳐 범위가 뒤집혔다. 단위 테스트는 7줄짜리만 봐서 놓침.
  2. 첫 스냅샷에서 줄이 서로 겹치고 긴 문단 둘째 줄이 잘림. 빗금·막대를 칸 안에 글자와 나란히 놓았더니, 글자 기준선 맞춤(`firstTextBaseline`)이 기준선 없는 막대의 아래 끝을 기준선으로 봐서 글자를 한 줄 아래로 밀었다. 빈 문단은 높이가 0이었다.
- **수정**: 1은 겹치면 접지 않게 고치고 간격 0~6줄을 모두 보는 테스트 추가. 2는 막대를 칸 위에 겹쳐 그리고(`overlay`), 빈 문단은 공백 한 칸으로 한 줄 높이를 둠 → 다시 찍어 확인.
- **측정**: perf.sh는 아직 안 돌림(키 입력·회차 전환·실행 경로는 판을 열지 않으면 바뀌지 않음). 비교 엔진 시간은 11c 측정 그대로(5,000자 0.7ms, 10만 자 16.9ms).

## 메모 단 스냅샷은 정리에서 지키기 (커밋 전)
- **이유**: 사용자 결정 "메모는 지키는 방향으로"(PLAN 결정 17). 메모를 단 것은 "남겨야지"라는 뜻이라서.
- **결과**: `pruneSnapshots`가 메모(`.memo`)가 있는 `auto`·`leave`를 세지도 지우지도 않는다. 목록을 읽은 뒤 지우기 직전에 메모가 붙었어도 건너뛴다. 설정 창 설명에 "메모를 단 것은 지우지 않아요" 추가. 테스트 `pruneRemovesMemoOfRemovedSnapshot`(메모도 함께 지움)을 `pruneKeepsSnapshotsWithMemo`로 바꿈. NovelCore 93개, 앱 103개(건너뜀 8) 통과.
