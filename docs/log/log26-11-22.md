- **이유**: 입력기 실험에서 macOS 27 두벌식이 표시된 글자 없이 조합한다는 것을 알았고, 그러면 지금 앱의 "조합이 끝난 한 글자가 한 단위" 규칙이 깨질 수 있었다. 사용자가 확인을 요청했다.

- **결과**: `ManuscriptTextView.insertText`에서 새 글자는 직접 한 단위(`InputUndoUnit`, 참조형)로 기록하고 NSTextView의 기록은 끈다. 입력기가 그 글자를 고치면 범위만 늘린다. 되돌리기는 범위를 검사하고 반대 기록을 직접 남긴다. 표시된 글자 방식과 다른 범위의 바꾸기는 예전 길 그대로. 실제 앱에서 ⌘Z 한 번에 한 글자, ⇧⌘Z로 복원, 이어 친 글이 디스크에 있음(증거 `build/verify/evidence/20261122-093339-undo-syllable`). 검증 스킬에 `keys.swift`.

- **수정**: ① 직접 기록 방식으로. ② 되돌리기 동안 NSTextView 기록을 끄고 반대 기록을 직접 남김, 범위 밖이면 아무것도 안 바꿈. ③ 테스트는 보이는 글이 바뀐 단계만 세게 바꾸고, 실제 앱에서 빈 단계가 없는 것을 따로 확인했다.

- **결과**: `TextReplace.replacing/count/canReplace`, `ReplacementPlan`·`ProjectStore.replacementPlan`(열린 회차는 넘겨받은 글, 나머지는 파일과 그 상태 `DiskVersion`), `SnapshotKind.replace`(`바꾸기 전`). `TextSearch.matches`가 쓰던 찾기 고리를 `forEachHit`로 떼어 바꾸기도 같이 쓴다. 새 본문은 뒤에서부터 고치는 대신 앞에서부터 이어 붙여 만든다(찾은 곳이 많아도 한 번 훑기). 테스트 13개(대소문자, NFD, 이모지, `\r\n`, 바꿀 말에 찾는 말이 든 경우, 찾기와 개수가 같음, 상한 없음, 취소). 검색 성능 그대로.

## 13단계 ② 실행·스냅샷·저장 (7dc92be)

- **이유**: 작품 전체 바꾸기를 실제로 실행한다. 검색 패널에서 바꿀 말을 넣고 모두 바꾸면 회차마다 안전하게 바뀌어야 한다.
- **근거**: PLAN 14장 2번·7번 ②. 첫 설계(센 글과 다르면 건너뜀)를 보인 뒤 사용자 결정: "웬만해서는 바뀌게, 작가가 바꾸고 싶은데 안 바뀌면 안 된다, 글쓰기가 매끄러워야", 되돌리기는 회차를 골라서(기본 모두 선택, 미리 보기), 바꿀 때 바꾸기 전·바꾼 뒤 스냅샷과 자동 메모. PLAN 14장 2·5번, 9장 4번, 미결정 21에 적음.
- **결과**: `ProjectReplace`(끝까지 다시 세기 → 확인 창 → 회차마다 바꾸기, 열린 회차는 맨 끝, 휴지통으로 간 회차는 조용히 뺌, 토스트 문구는 0을 빼고). `EpisodeAutosaver.replace`(지금 글에서 다시 찾기, 메모리에 남은 글 우선, 파일은 새로 읽은 상태로 조건부 쓰기, 엇갈리면 3번까지, 쓰기 실패는 저장 실패처럼 붙잡음). `ManuscriptTextView.replaceOccurrences`(`shouldChangeText(inRanges:)`로 실행 취소 한 단위, 뒤에서부터 바꿈, 커서를 바뀐 길이만큼 옮김, 화면 맨 위 글자와 그 줄 안 위치 유지). `TextReplace.ranges`, `SnapshotKind.replaced`(`바꾼 뒤`), 스냅샷 시각을 받는 `takeReplace`. 테스트 앱 15개(+NovelCore 1개). 실제 앱 확인(증거 `build/verify/evidence/20261122-154016-replace-all`).
- **에러**: ① 첫 설계는 센 뒤 바뀐 회차를 모두 건너뛰어 사용자가 거절(테스트는 통과했었음). ② 확인 창 `모두 바꾸기`가 `Task` 안에서 `pending`을 읽으면, 창이 닫히며 바인딩이 먼저 `pending`을 비워 실행되지 않을 뻔함. ③ `Task.detached`에 MainActor 구조체(`Pending`)를 통째로 넘겨 Swift 6 격리 오류, 테스트 도우미의 async 자동 클로저도 Sendable 오류. ④ 실제 앱에서 확인 창에 넣지 않은 `다시 묻지 않기` 체크 칸이 보임(사이드바 되돌리기 창의 `.dialogSuppressionToggle`이 환경으로 퍼짐, 이전부터 있던 문제). ⑤ 실제 앱의 ⌘Z는 앱이 뒤에 있어 편집 메뉴가 꺼져 확인 못 함(화면 제어 승인이 시간 안에 안 옴).
- **수정**: ① 바꾸는 순간의 글에서 다시 찾고, 조합 중이면 기다렸다 찾은 자리만 바꾸도록 다시 만듦. ② 창이 보여 준 값을 받아 `confirm(pending)`. ③ 필요한 값만 지역 상수로 꺼내 넘김, 도우미는 MainActor 메서드로. ④ 고치려면 허락 필요(PROGRESS 다음 할 일). ⑤ 단위 테스트로 확인, 손 확인으로 남김.

## 확인 창의 '다시 묻지 않기' 범위 고치기, 전체 바꾸기 ⌘Z 실제 앱 확인 (bea8946)

- **이유**: 실제 앱에서 전체 바꾸기 확인 창에 넣지 않은 `다시 묻지 않기` 체크 칸이 보였다. 누르면 사이드바 되돌리기 확인이 멈출 수 있다.
- **근거**: 7dc92be 실제 앱 확인에서 발견, 사용자 허락("어 그리고 권한 요청 보내").
- **결과**: `UndoConfirmationDialog`가 확인 창을 `content.background { Color.clear… }`에 달아 `.dialogSuppressionToggle`이 그 창에만 걸린다. 실제 앱: 바꾸기 확인 창엔 칸 없음, 사이드바 되돌리기 창엔 있음·되돌리기 동작 그대로. 편집기 실행 취소 한 번이면 열린 회차가 바꾸기 직전으로(되돌린 자리 선택, 화면 그대로), 실행 복귀로 다시. 증거 `build/verify/evidence/20261122-155355-replace-undo-dialog`. 테스트 그대로 통과(NovelCore 156개·앱 211개).
- **에러**: ① 이 문제는 이전부터 있었다(회차 이름·목표 글자 수 창 등에도 붙었을 것). ② 화면 제어로 보낸 ⌘Z 키는 효과가 없었다(누른 곳이 본문 왼쪽 여백이라 초점이 편집기에 안 간 듯, 화면에 전체 선택처럼 회색이 보임). ③ 앞선 확인에서는 앱이 뒤에 있어 편집 메뉴의 실행 취소가 꺼져 있었다.
- **수정**: ② ③ 앱을 앞으로 가져온 뒤 편집 메뉴의 `실행 취소`·`실행 복귀`(⌘Z와 같은 명령)로 확인.

## 13단계 ③ 결과 미리 보기·바꾼 회차 목록 (커밋 해시는 다음 커밋에)

- **이유**: 바꾸기 전에 무엇이 어떻게 바뀔지 보이고, 바꾼 뒤에는 어느 회차가 바뀌었는지 보고 바로 비교할 수 있어야 한다.
- **근거**: PLAN 14장 1번(미리 보기)·3번(바꾼 회차 목록, 스냅샷 판이 `바꾸기 전`을 골라 둔 채, 사용자 결정), 7번 ③. 사용자 "③ 시작".
- **결과**: `SearchMatchRow`에 바꿀 말 미리 보기(`diffRemoved`+취소선, `diffAdded`). `ProjectReplace.finished`(회차 순서로, 문구 포함, 검색어를 고치거나 패널을 닫으면 비움). `SearchPanel`의 바꾼 회차 목록·상태 줄. `WorkspaceView.showReplaced`: 회차를 옮기고 편집기에 본문이 올라간 뒤(`ManuscriptEditor.onShown` → `EpisodeEditorPane.onShown`) 판을 연다. 이미 그 회차면 바로. `SnapshotBrowser.preferredID`(없으면 가장 최근). 토스트 `바꾼 곳 보기`. 테스트 3개(처음 고를 스냅샷, 못 찾으면 최근 것, 바꾼 회차 목록 순서·비우기). 실제 앱 확인(증거 `build/verify/evidence/20261122-155952-replace-list`).
- **에러**: ① 판은 편집기의 지금 본문과 비교하므로, 회차를 옮기자마자 열면 옛 회차 본문과 비교할 수 있다(설계 중 발견). ② 실제 앱 확인 중 창 크기가 바뀌어 좌표 클릭이 빗나가 1화가 열리고 목록에 글자가 쳐졌다(본문은 그대로). ③ 토스트 `바꾼 곳 보기`는 2초 안에 누르지 못해 확인 못 함. ④ 대기 메모리 79 → 95MB(이번 측정, malloc은 그대로 38MB).
- **수정**: ① 편집기가 본문을 넣은 뒤 한 차례 뒤에 알리는 `onShown`을 기다려 연다. ② 요소 번호로 다시 눌러 진행. ③ 목록 줄과 같은 함수라 남겨 둠. ④ 같은 코드에서도 79~95MB를 오가던 기기 상태 차이와 같은 모양, 목표 안이라 17단계에서.
