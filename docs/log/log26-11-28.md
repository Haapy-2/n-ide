- **이유**: 결정 30 순서 1번(PLAN 18장 3번). 이 테스트는 테스트 앱이 죽어 `NOVEL_WRITER_DAY=1`일 때만 돈다.

  - 앱 `ImageImporter`(메인 밖에서 읽고 다른 형식은 ImageIO로 PNG, 붙여 넣기 판에서 파일이 먼저·글이 있으면 그림 데이터는 무시), `ImageInsertion`(파일을 다 쓴 뒤 조합이 끝나면 줄 넣기, ⌘Z 한 단위 "그림 넣기", 그사이 회차를 바꾸면 줄은 넣지 않고 파일·이름만 남김, 깨진 상자 오른쪽 클릭 `다른 그림으로 바꾸기…`·`작품에 넣기`, 실패 알림), 편집 메뉴 `그림 넣기…`(단축키 설정 표에도), `ProjectModel.addImageNames`(이름은 ⌘Z 대상 아님, G2).
  - 테스트: NovelCore 269개(새 12), 앱 343개(새 13, 건너뜀 17) 통과, NovelCore iOS 빌드 성공.
  - 실제 앱: 편집 → 붙여넣기로 Finder 파일 붙여 넣기 → 그림 표시, `images/`에 원본과 같은 바이트, 원고 줄, `project.json` 이름 "바다". 편집 메뉴 "그림 넣기 실행 취소" 한 번에 원래 글. `그림 넣기…` 메뉴는 "그림 넣기" 열기 창이 뜨는 데까지.
  - 미확인(손 확인 목록에 넣음): Finder에서 끌어 놓기, 열기 창에서 그림 고르기, 깨진 상자 오른쪽 클릭(앱 테스트로만 확인).
- **에러**:
  - 앱 테스트 하나가 "freed pointer was not the last allocation"으로 죽음. 기다리는 함수의 클로저를 탈출 가능으로 바꾸고, `Task.yield()`를 넣어 봤지만 그대로(효과 없음).
  - 작품 밖 그림 테스트가 범위 밖 접근으로 죽음: 시험 파일 이름에 빈칸이 있어 그림 줄로 읽히지 않음.
  - 실제 앱: osascript로 올린 클립보드가 비어 있었고, 한글 자판에서 ⌘V가 ⌘A로 감(알려진 함정), 열기 창은 다른 프로세스라 글자 입력이 막힘, Finder 끌기는 첫 번째는 시작되지 않고 두 번째는 알림 센터가 앞에 나와 멈춤(두 번에서 멈춤).
- **수정**: 같은 테스트를 동기로 돌려 보니 진짜 원인은 "undo 그룹 없이 등록" 예외(테스트 편집기가 `groupsByEvent`를 끔)였고, 비동기 테스트 안에서 예외가 나며 죽은 것. 조합 흉내를 undo 그룹 안에서 하게 고치고 앞의 두 시도는 되돌림. 파일 이름에서 빈칸을 뺌. 클립보드는 AppKit으로 다시 올리고, 붙여넣기는 편집 메뉴를 눌러서 함.

## ③b 버그 조사: 그림 데이터 끌어 놓기가 거절되던 것, 창을 닫으면 조합 대기가 편집기를 잡고 있던 것 고침 (6b538f6)

- **이유**: 사용자 "다음 작업으로 버그 가능성 조사 하고 검증하고 해결해".
- **근거**: ③b 코드에서 의심 넷을 골라 하나씩 테스트로 확인. ① 오른쪽 클릭 메뉴가 여러 편집기가 함께 쓰는 메뉴라 항목이 쌓이는지 ② 글 전용 편집기가 그림 데이터 끌기를 받는지 ③ 클립보드에 그림 데이터만 있을 때 붙여넣기가 켜지는지 ④ 조합 중 창을 닫으면 대기가 끝나는지.
- **결과**:
  - ① 아님: 부를 때마다 새 메뉴라 쌓이지 않음(회귀 테스트로 남김). ③ 아님: 켜짐(클립보드를 저장·복원하는 일회성 시험, 남기지 않음).
  - ② 진짜: 미리 보기·사진·브라우저에서 그림을 끌면 끄는 동안 "받지 않음"(0)이라 놓을 수 없었다. 파일 끌기는 받음. `draggingEntered`·`draggingUpdated`가 거절할 때 그림이면 복사로 답하게 고침. 가짜 끌기 객체로 파일·데이터 둘 다 놓은 자리에 들어가고 줄이 깨지지 않음을 테스트.
  - ④ 진짜: 창을 닫는 길에는 조합을 끝내는 곳이 없어, 그림 파일을 쓰는 사이 창을 닫으면 0.05초마다 깨는 대기가 영원히 돌며 편집기를 놓지 않았다(가만히 있을 때 CPU 0% 규칙 위반). 편집기가 창에서 빠지면 기다림을 멈추게 고침. 고침을 빼면 새 테스트가 실패하는 것을 확인.
  - 테스트: NovelCore 269개, 앱 346개(새 3, 건너뜀 17) 통과, NovelCore iOS 빌드 성공. perf.sh는 끌기·넣은 뒤 대기만 바뀌어(키 입력·저장·전환 길 아님) 건너뜀.
- **에러**: 처음엔 `dragOperation(for:type:)`를 고쳤으나 효과 없음: 글 전용 편집기는 읽을 수 없는 종류(TIFF)에 대해 그 함수를 아예 부르지 않는다.
- **수정**: 끌기 들어옴·움직임 단계에서 직접 답하는 방식으로 바꿈.

## 그림 기능 넓은 버그 조사와 A~D 고침: Enter 뒤 그림 줄 색인, 그림 아래 줄 ⌫, 그림 옆 ⌥⌫·⌥⌦, 그림 옆 Tab (대기)

- **이유**: 사용자 "추가로 조사 범위 확대해서 조사해" → 보고(진짜 버그 2, 불편 2, 위험 3) → "추천대로 고쳐"(A~D 지금, E·F는 따로).
- **근거**: 임시 시험(무작위 편집 6만 번을 전체 다시 읽기와 비교, 편집기 동작 여러 개, 썸네일 메모리 계산). 시험 파일은 지움.
- **결과**:
  - A(진짜): 줄 바꿈으로 끝나는 편집(Enter, 줄 붙여 넣기)이 다음 줄 앞을 바꾸면 그 줄을 다시 읽지 않아, `글![](…)`에서 `![]` 앞 Enter 뒤 그림이 마크다운 글로 보였다(무작위 6만 번 중 37번). `ImageLineIndex.update`가 편집 뒤 한 글자까지 문단을 잡게 고침. 고정 씨앗 무작위 1,000×20번 테스트와 두 경우 테스트(고침을 빼면 실패 확인).
  - B(진짜): 그림 아래 글 줄 맨 앞 ⌫가 그 글을 그림 줄에 붙여 그림이 마크다운으로 바뀜. ⌦ 쪽처럼 커서만 그림 끝으로(빈 줄이면 전처럼 빈 줄을 지움).
  - C: 그림 옆 ⌥⌫·⌥⌦가 거절되어 아무 일도 없던 것 → ⌫·⌦ 규칙으로(바로 뒤·앞이면 그림 통째, 아래·위 줄 끝이면 커서만). 기존 테스트 `testWordDeleteInsideThePathDoesNothing`은 바뀐 동작(사용자 승인)에 맞춰 `testWordDeleteBesideAnImageLineActsLikeDelete`로 고침. 경로를 자르는 일이 없다는 검사는 그대로.
  - D: Tab은 `insertText`·`keyDown` 글자 경로를 타지 않아 그림 줄 안에 숨은 탭이 됨 → 다른 글자처럼 새 줄을 먼저 염.
  - 실제 앱: A는 `![]` 앞 Enter 즉시 회색 상자·글자 수에서 빠짐, B·D는 두벌식 실제 키로 "뒤"가 새 줄에 조합, 그 줄 앞 ⌫ = 커서만 그림 끝, Tab = 따로 한 줄(디스크 `…png)\n\t\n뒤`). ⌥⌫는 키 도구에 ⌥가 없어 테스트로만.
  - 남긴 것(따로 한 단계): E 썸네일 메모리(1600×900 그림 20장에 76MB, 목표 +20MB, 화면 밖 그림을 버리지 않음), F iCloud에서 내려받지 않은 그림의 머리를 메인 스레드에서 읽어 멈출 수 있음(재현 못 함), G 스냅샷 비교의 그림 줄(G14, 계획된 일).
  - 문제없음: 오른쪽 클릭 메뉴 쌓임, 손으로 친 `![](…)`, ⌘⌫, 글자 순서 바꾸기, 그림 앞 스페이스.
  - 테스트: NovelCore 272개(새 3), 앱 349개(새 3, 건너뜀 17) 통과.
- **에러**: 컴퓨터 유스의 `app_type`·⌫는 접근성으로 글자를 바꿔 `keyDown`·`deleteBackward`를 거치지 않아 B 확인이 되지 않았고(그림 줄 뒤에 "뒤"가 붙음), 백그라운드 ←키는 한 번만 들어감. 되돌리기가 엉켜 앱을 새로 띄움. 새 테스트 하나는 본문에 그림이 둘이라 "경로 글자가 없다" 검사가 틀렸음.
- **수정**: 커서는 클릭 위치로 놓고, B·D는 `keys`(실제 키 코드)로. 테스트 검사는 "그림 줄 수"로.
