# 2026-11-25 작업 기록

## ⌘D 다른 자리 커서를 맨 앞 커서와 같이 깜빡이게 (bda8655)

- **이유**: 사용자가 "⌘D로 그린 커서를 원본 커서랑 똑같이 깜박여 줘, 주기는 무조건 똑같이"라고 요청했다. 다른 자리 커서가 깜빡이지 않고 켜진 채로 남았다.
- **근거**: 빈 시험 창(`NSTextView` 하위 클래스, 레이어 있음·없음 둘 다)에서 호출을 찍어 봄: 시스템은 약 0.56초마다 커서 칸을 다시 그리고, 켤 때만 그 그리기 바로 뒤에 `drawInsertionPoint(turnedOn: true)`를 부른다. 깜빡임으로 끌 때는 `turnedOn: false`를 한 번도 부르지 않았다. 기존 코드는 `turnedOn` 값으로 켜고 껐기 때문에 한 번 켜지면 창이 비활성화될 때까지 꺼지지 않았다. 또 커서 칸 다시 그리기 요청에 다른 칸을 붙이면 한 그리기에 함께 들어오고 `drawInsertionPoint`의 그리기 범위도 그만큼 넓어짐을 확인했다.
- **결과**: 따로 타이머 없이 시스템 깜빡임에 묶음. ① 가는 커서 칸 다시 그리기 요청(`isCaretSized`)에 다른 자리 커서 칸을 붙인다. ② 그리기가 맨 앞 커서 칸을 덮으면(`needsToDraw`) 다른 커서도 꺼짐. ③ `drawInsertionPoint(turnedOn: true)` 안에서 맨 앞 커서와 함께 다른 커서도 그린다(같은 그리기, 같은 화면 갱신). 앱 테스트 2개(켜는 그리기에 다른 커서가 그려짐, 다시 그리면 사라짐: 고치기 전 둘 다 실패를 확인). 실제 앱(앞에 띄운 창, ⌘D 세 자리 + 스페이스)에서 16번 찍어 매번 세 커서가 모두 켜지거나 모두 꺼짐, 하나만 다른 순간 없음(증거 `build/verify/evidence/20261125-103339-multi-cursor-blink`, 화면은 대화에 남김). NovelCore 201개·앱 252개(건너뜀 15) 통과. 성능은 따로 재지 않음: 바뀐 것은 여러 커서일 때 깜빡임마다 다른 커서 칸 계산뿐이고, 커서 100개 키 입력 측정은 13-2 ④에서 한다.
- **에러**: ① 첫 시험 창은 터미널에서 띄워 키 창이 되지 않아 커서가 깜빡이지 않음. ② zsh에서 `$mode`가 낱말로 나뉘지 않아 일부 측정 모드가 꺼진 채로 돌았다. ③ 꺼짐 테스트의 비교 그림을 새 편집기로 만들었더니 배경이 비어 있었다. ④ 백그라운드 조작으로는 창이 키 창이 아니라 실제 앱에서 깜빡임이 안 보인다.
- **수정**: ① 조금 뒤에 `activate`. ② 측정은 레이어 있음/없음 결과만 씀. ③ 같은 편집기에서 여러 커서만 버리고 다시 그려 비교. ④ 사용자 허락을 받고 검증 앱을 맨 앞에 띄워 확인. 기능 지도에 적음.

## 13-2 ③-1 여러 커서 화살표·지우기 (8aec97d)

- **이유**: 13-2 다음 조각(PLAN 16장 6번 ③, E5). 지금은 화살표·지우기 키를 누르면 여러 커서가 풀린다.
- **근거**: 사용자 승인("진행, ⌘C·⌘X도 VS Code처럼"). 측정: 편집기 이동 명령을 커서마다 부르면 커서 1,000개(10만 자)에 키 하나 약 90ms(목표 16ms 초과), 직접 계산은 1ms 미만. `NSAttributedString.nextWord`가 편집기 ⌥←/→와 시험 글 56자리 모두 같음.
- **결과**: NovelCore `MultiCursor.Selection`(붙박인 끝·움직이는 끝), `move(to:extending:)`(만난 자리 합치기, 방향은 묶음의 첫 선택), `deleteTargets(_:to:)`(⌫ 전용 함수를 대신함), 글자·문단 경계, `copiedText`·`pasteTexts`. 앱 `MultiCursorMovement.swift`: 이동 명령 38개·지우기 6개·화면 넘기기 7개 표, 커서마다 목표 자리 계산(↑↓는 자리마다 가로 위치 기억). 앱 테스트: 커서 하나일 때 편집기와 모든 커서 자리·모든 이동/지우기 명령 비교(접히는 긴 문단, 이모지, 자모를 따로 적은 한글, 빈 줄, 끝 줄바꿈), 여러 커서 동작 7개. NovelCore 207개·앱 261개(건너뜀 15) 통과.
- **에러**: ① 비교 테스트가 처음 259곳 다름. 원인은 커서 가로 위치를 `boundingRect`(글자 모양이 그려지는 넓이)로 잰 것: Pretendard에서 실제 커서 자리보다 약 12pt 왼쪽이라 ↑↓가 한 글자씩 덜 갔다. ② 단계의 다른 자리 커서 그리기도 같은 함수를 써서 조금 왼쪽에 그려졌을 것. ② 줄이 접히는 자리: 프로그램이 놓은 커서는 앞 줄 끝으로 보는데 계산은 다음 줄 처음으로 봄. ③ 글 끝 빈 줄이 아직 배치되지 않아 ⌘⌫·⌘⌦가 앞 줄을 지움. ④ 편집기 ⌘⌦는 줄 끝에서 줄바꿈을 지움. ⑤ 테스트 실수: 지운 뒤의 글로 지울 곳을 계산, 자리 번호를 잘못 셈.
- **수정**: ① 커서 자리는 글자가 놓인 자리(`location(forGlyphAt:)`), 글 끝만 빈 범위 선택 칸. ② 여러 커서는 다음 줄 처음으로 통일하고 비교 테스트도 그렇게 놓음. ③ 글 끝을 볼 때 배치를 끝까지. ④ `deletionStop`. ⑤ 테스트 고침.

## 13-2 ③-2 붙여 넣기 나눠 넣기·⌘C/⌘X, 측정 (e7e96f2)

- **이유**: ③의 남은 조각(E7)과 성능 확인(16장 P1, SPEC 8장 키 입력 16ms).
- **근거**: 사용자 결정(⌘C·⌘X는 VS Code처럼 이어 복사). VS Code `multiCursorPaste: spread`.
- **결과**: `copy`·`cut`·`paste`·`pasteAsPlainText`가 여러 커서일 때 모든 자리에서(붙여 넣기·잘라내기는 ⌘Z 한 단위). 테스트는 사용자 클립보드 대신 따로 만든 붙여 넣기 판을 쓴다. 앱 테스트 4개. NovelCore 207개·앱 265개(건너뜀 15) 통과. 측정(Release, 10만 자, 부하 평균 5~6.5, 임시 테스트라 커밋 안 함): 이동은 커서 1,000개에서 → 0.3ms, ⌥→ 0.5ms, ⌘→ 0.6ms, ⇧→ 0.3ms, ↓ 12.5ms(통과). **글을 고치는 키는 미달**: 커서 100개 ⌥⌫ 35ms, 한 글자 입력은 커서 2개라도 글 처음과 끝이면 69ms(앞 1천 자 안 100개는 4.9ms, 커서 하나 2.9ms).
- **에러**: ① ↓를 `characterIndexForInsertion`으로 고르니 커서 1,000개 33ms(Debug). ② Release 설정으로 `@testable` 테스트가 빌드되지 않음. ③ 위 미달.
- **수정**: ① 글자 칸(`glyphIndex(for:)`)으로 고르고 한 글자 가운데는 가까운 끝으로 → 1,000개 12.5ms(Release), 비교 테스트 그대로 통과. ② perf.sh처럼 `ENABLE_TESTABILITY=YES`. ③ 원인: 모든 자리를 `beginEditing`/`endEditing` 한 번으로 묶어서 고친 범위가 첫 자리~끝 자리 전체(최대 10만 자)가 되고, 그만큼을 다시 처리한다(16장 P1에서 정한 방법이 거꾸로 작용). 묶지 않고 자리마다 고치는 것을 임시로 재 보니 커서 2개 1.3ms, 100개 3.2ms, 1,000개 21.4ms. 되돌려 두고 사용자에게 보고(고치지 않음).

## 13-2 ③-3 여러 커서 고치기를 자리마다 (b824614)

- **이유**: ③-2 측정에서 글을 고치는 키가 목표(16ms) 미달.
- **근거**: 사용자 승인("네, 바꿔 주세요"). 임시 측정으로 원인(묶음 범위가 첫 자리~끝 자리 전체)과 대안 확인.
- **결과**: `applyMultiCursor`와 되돌리기가 `beginEditing`/`endEditing` 없이 뒤에서부터 자리마다 고친다(`replaceEach` 한 곳). PLAN 16장 P1 고침. Release 다시 측정(10만 자, 부하 평균 15.9, 아홉 번 가운데값): 글자 입력 커서 2개(처음·끝) 0.8ms·100개 2.0ms·1,000개 12.5ms, ⌥⌫ 0.8·2.0·12.2ms. 모두 통과. NovelCore 207개·앱 265개(건너뜀 15) 통과.
- **에러**: 전체 테스트 첫 실행에서 `ProjectModelTests.testUndoAndRedoReorder`가 한 번 실패(순서가 되돌려지지 않은 채로 읽힘). 따로 세 번·전체 다시 한 번은 통과. 이 테스트는 되돌리기 뒤 100ms를 고정으로 기다려 저장을 확인해서, 기계가 바쁠 때(부하 평균 6~16) 흔들리는 것으로 보인다(추론). 이번 변경과 상관없는 파일.
